# 실험 증거 및 가설 영향 분석 — v0.1

연구노트: *Timing-Contract-Aware MLIR Compilation for AI Plugins in NASA OnAIR/cFS*
문서 목적: 지금까지 수행한 실험 중 **가설(H1/H2/H3)의 유지·수정·기각에 직접 영향을 주는 결과만** 정리한다.

---

## 요약

- **TOPIC** — OnAIR Learner 플러그인을 MLIR/IREE로 AOT 컴파일했을 때의 실행 특성을, 실제 OnAIR 플러그인 인터페이스 위에서 측정한 1차 실험 결과.
- **Problem** — 컴파일된 Learner가 Python(NumPy/BLAS) Learner보다 모든 모델 크기에서 6–9배 느렸고, 소형 모델에서는 지연 분산까지 더 나빴다. H1을 현재 서술 그대로 유지할 수 없다.
- **Solution** — 원인은 마샬링이 아니라 lowering 품질이며, 동일 모델에서 컴파일 설정만으로 median 1.87배·순위 역전이 발생함을 확인했다. 연구의 주장 축을 H1(AOT=빠름)에서 H2/C3(계약 인지 lowering 선택)로 이동시킨다.

## 0. 증거 등급 선언

| 항목 | 값 |
|---|---|
| 실행 플랫폼 | 공유 VM, 1 vCPU (Intel Xeon @2.10GHz), 3.9 GiB RAM, Ubuntu 24.04 |
| 플랫폼 잡음 (`platform_check.py`) | median 790.1 µs, p99 1319.5 µs, max 1786.6 µs |
| 잡음 비 | ratio_p99 = **1.67**, ratio_max = **2.26** |
| **timing_grade** | **FUNCTIONAL_ONLY** |

**해석 규칙(본 문서 전체에 적용)**
1. 절대 지연값은 논문 증거로 인용하지 않는다.
2. 동일 호스트에서 연속 측정한 **구현 간 비율**만 논의하며, 그 비율이 잡음 비(1.67×/2.26×)를 명확히 초과할 때만 방향성 결론을 내린다.
3. 아래 관측된 격차 6–9배와 설정 편차 1.87배는 이 기준을 넘는다. 반면 **분산 지표(p99/median)의 차이 일부는 이 기준 안쪽**이므로 잠정으로만 취급한다.

## 1. 실험 E0 — OnAIR 통합 가능성 (가설 전제)

**대상 전제**: 연구노트 §6–7 "OnAIR core를 변경하지 않고 컴파일된 Learner를 삽입할 수 있다."

**방법**: `onair.src.ai_components.ai_plugin_abstract.ai_plugin.AIPlugin`을 상속한 두 플러그인
(`CompiledLearner` = IREE 아티팩트, `PythonLearner` = NumPy)을 작성하고,
OnAIR 자신의 로더 `onair.src.util.plugin_import.import_plugins`로 적재,
`csv_parser` 텔레메트리 소스(9필드)로 `driver.py` 완주.

**결과**: **PASS.** OnAIR core 코드 변경 0줄.

**부수 발견(재현에 필요)**: `AIPlugin.__init__`이 `ServiceManager()` 싱글턴을 생성하므로,
플러그인 인스턴스화 이전에 `ServiceManager({})`로 1회 초기화하지 않으면
`ValueError: 'service_dict' parameter required on first instantiation`으로 실패한다.

**가설 영향**: H1/H2/H3의 **공통 전제가 성립**함을 확인. 아키텍처 변경 리스크는 제거됐다.

## 2. 실험 E1 — 모델 크기 스윕 (H1 직접 검증)

**설계**: MLP `1×9 → hidden → 2`, `linalg.matmul` 2단.
동일 가중치·동일 입력 프레임(실 텔레메트리 CSV), 동일 플러그인 인터페이스.
IREE 백엔드 `llvm-cpu`, 런타임 드라이버 `local-sync`, 프로파일 `fast`.
경계는 세 가지를 분리 기록: **L1_kernel**(추론 호출만), **L2a_update**(입력 패킹), **L2b_reason**(`render_reasoning()` 전체).

### 2.1 L1_kernel (µs)

| hidden | compiled median | python median | **비율** | compiled p99 | python p99 | n |
|---:|---:|---:|---:|---:|---:|---:|
| 16 | 13.10 | 1.94 | **6.8×** | 34.20 | 4.26 | 6000 |
| 64 | 13.79 | 1.94 | **7.1×** | 38.94 | 3.72 | 6000 |
| 256 | 15.32 | 2.06 | **7.4×** | 39.30 | 4.62 | 6000 |
| 1024 | 22.04 | 3.14 | **7.0×** | 49.85 | 7.99 | 6000 |
| 4096 | 51.50 | 5.40 | **9.5×** | 103.19 | 10.89 | 1440 |
| 16384 | 152.50 | 17.86 | **8.5×** | 280.22 | 40.85 | 1440 |
| 65536 | 775.81 | 123.37 | **6.3×** | 1081.12 | 204.04 | 1440 |

### 2.2 L2b_reason (µs, median)

| hidden | compiled | python | 비율 |
|---:|---:|---:|---:|
| 16 | 19.09 | 2.15 | 8.9× |
| 1024 | 28.41 | 3.39 | 8.4× |
| 16384 | 164.84 | 18.12 | 9.1× |
| 65536 | 802.58 | 123.94 | 6.5× |

### 2.3 관측

- 모델을 **4096배** 키워도(16 → 65536) 교차점이 나타나지 않는다.
- 비율이 크기에 따라 단조 감소하지도 않는다(6.8 → 9.5 → 6.3).
- L2b는 L1보다 비율이 더 크다 — 래퍼 비용이 컴파일 쪽에 더 불리하게 작용.

**가설 영향 (H1)**: H1의 "속도" 측면은 **이 조건에서 기각**된다.

## 3. 실험 E2 — 지연 분산 (H1의 predictability 측면 직접 검증)

H1의 핵심은 속도가 아니라 **tail과 variability 감소**다. 상대 분산으로 본다.

| hidden | compiled p99/med | python p99/med | compiled max/med | python max/med |
|---:|---:|---:|---:|---:|
| 16 | 2.61 | 2.20 | 45.61 | 18.05 |
| 64 | 2.82 | 1.92 | 44.23 | 16.25 |
| 256 | 2.56 | 2.25 | 37.78 | 22.18 |
| 1024 | 2.26 | 2.54 | 28.79 | 11.29 |
| 4096 | 2.00 | 2.02 | 4.27 | 7.85 |
| 16384 | 1.84 | 2.29 | 3.50 | 4.66 |
| 65536 | **1.39** | 1.65 | 2.96 | 2.53 |

**관측**
- **소형 모델(16–256)에서 컴파일 쪽의 상대 분산이 더 나쁘다.** p99/med 2.6–2.8 vs 1.9–2.3, max/med 38–46 vs 16–22.
- **대형 모델(16384–65536)에서 역전**되어 컴파일 쪽 p99/med가 더 작아진다(1.39 vs 1.65).
- 단, 이 역전 폭(1.39 vs 1.65 = 1.19배)은 플랫폼 잡음 비(1.67배) **안쪽**이다.

**가설 영향 (H1)**:
- 소형 모델 구간에서는 H1이 **반대 방향의 증거**를 만난다 — 컴파일이 예측가능성을 오히려 낮췄다.
- 대형 구간의 유리한 신호는 **현 플랫폼에서 판별 불가**. `platform_check` PASS 환경에서 재측정이 필요한 유일한 H1 잔여 가능성이다.
- 결론: H1은 "AOT는 예측가능성을 개선한다"에서 **"AOT의 예측가능성 효과는 모델 규모에 의존하며, 소형 텔레메트리 모델에서는 관측되지 않는다"** 로 재서술해야 한다.

## 4. 실험 E3 — 원인 규명: 마샬링 가설 배제

**방법**: 연산이 없는 항등 아티팩트(`func @infer(%x) -> %x`)를 컴파일해 호출 비용만 측정(n=20000, warmup 2000).

| 지표 | 값 |
|---|---:|
| identity-call median | **4.70 µs** |
| identity-call p99 | 12.06 µs |

**추론**: Python↔IREE 마샬링 고정비는 약 5 µs다.
hidden=65536에서의 절대 격차 **652 µs**(775.8 − 123.4)를 설명할 수 없다.
→ **원인은 호출 오버헤드가 아니라 생성된 커널의 코드 품질**이다.
베이스라인 NumPy는 최적화된 BLAS GEMV를 호출하는 반면, 기본 플래그로 내린 `linalg.matmul`은 그에 미치지 못한다.

**가설 영향**:
- H1이 기각 방향인 이유가 "Python이 빨라서"가 아니라 "**컴파일 설정이 미흡해서**"임이 특정됐다 → H2로 문제를 이관할 근거.
- 동시에 **B0(NumPy/BLAS)는 약한 베이스라인이 아니라 강한 베이스라인**임이 확정됐다. 이를 약화시켜 승리를 만드는 서술은 금지한다.

## 5. 실험 E4 — lowering 설정 효과 (H2 직접 검증)

**설계**: hidden=16384 고정. **동일 MLIR·동일 가중치·동일 런타임(local-sync)**, IREE 컴파일 플래그만 변경. n=1500, warmup 300.

| lowering 설정 | median (µs) | p99 (µs) | p99/med | 아티팩트 (B) |
|---|---:|---:|---:|---:|
| default | 141.2 | 218.7 | 1.55 | 10,510 |
| `--iree-llvmcpu-target-cpu=host` | **82.3** | 135.2 | 1.64 | 11,718 |
| `+avx2,+fma` | 154.0 | 220.5 | 1.43 | 10,542 |
| `+avx512f,+avx512bw,+avx2,+fma` | 96.4 | 157.4 | 1.63 | 10,886 |
| (참고) numpy BLAS | 17.9 | 37.5 | 2.09 | — |

**관측**
1. 설정 간 median 편차 **1.87배** (82.3 ↔ 154.0). 플랫폼 잡음 비(1.67×)를 초과 → 유의한 신호.
2. **순위가 직관과 불일치**: `+avx2,+fma`를 명시한 설정이 default보다 **느리다**(154.0 vs 141.2).
3. **median 최적과 분산 최적이 다르다**: median 최소는 `host`(82.3, p99/med 1.64), p99/med 최소는 `+avx2`(1.43, median 154.0). 즉 **속도와 예측가능성이 함께 움직이지 않는다.**
4. 아티팩트 크기는 설정과 성능 사이에서 예측력이 없다.

**가설 영향 (H2)**: **강화됨.**
- H2의 전제 "여러 lowering configuration이 서로 다른 (C, M) 특성을 갖는다"가 실측으로 성립.
- 관측 2·3은 "성능 좋은 플래그를 고르면 된다"는 반론을 무력화한다. **선험적으로 알 수 없으므로 측정·선택 절차가 필요하다**는 것이 곧 §10의 문제 정식화이며, 연구노트가 지정한 유일한 컴파일러 기여(C3)의 필요성을 실증한다.
- 관측 3은 목적함수를 `min α·C + β·M`(§10)이 아니라 **분산 항을 포함한 다목적**으로 확장해야 함을 시사한다.

## 7. 연구 설계에 대한 함의

1. **주장 축 이동.** 논문의 1차 주장을 "AOT가 더 빠르다"에서
   **"lowering 선택이 실행 특성을 지배하며, 그 선택을 미션 타이밍 제약으로부터 유도할 수 있다"** 로 옮긴다.
   E4가 이 주장의 동기 데이터가 된다.
2. **베이스라인 정직성.** B0는 BLAS 기반 강한 베이스라인이다. 지연에서 이기려 하지 말고,
   B0가 제공하지 못하는 축 — **peak memory 상한, 정적 할당, 결정성, 비행 타깃 이식성** — 에서 비교한다.
3. **A-native 변형 필수.** Python 래퍼가 있는 한 약 5 µs 고정비가 항상 붙고(E3),
   L2b 비율이 L1보다 나쁘다(E1). cFS C 앱에 정적 링크한 변형에서만 계약이 온전한 의미를 갖는다.
4. **B2 추가.** "왜 MLIR이어야 하는가"에 답하려면 TFLite Micro(정적 아레나·단일 스레드) 베이스라인이 필요하다.
5. **목적함수 재정의.** E4 관측 3에 따라 median·p99·peak memory를 함께 다루는 다목적 선택으로 §10을 수정한다.
