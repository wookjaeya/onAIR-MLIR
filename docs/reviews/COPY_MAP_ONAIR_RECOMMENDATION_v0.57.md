# 복사·매핑 경로 및 OnAIR 증거 보강 권고안

- 작성일: 2026-09-14
- 검토 기준: onAIR-MLIR v0.57, 커밋 `f4b41dc484ffcc465ac3ddf1d6266b8dd5a26142`
- 성격: 직전 저장소 검토를 정리한 후속 작업 권고. 신규 실험 결과가 아니며, 수행 우선순위와 완료 기준은 **본인 분석·판단**이다.
- 기존 권고와의 관계: `MANDATORY_FOLLOWUPS_v0.57_RECOMMENDATION.md`의 조건부 map 검증에 **AArch64 cFS copy 경로 검증을 추가**한다. OnAIR의 신규 메모리 준수 실험을 필수화하지 않는다.

## 2. 기존 증거와 남은 공백

### 2.1 복사 경로

E29에는 정렬 스윕 64셀에서 map 32건·copy 32건이 기록돼 있다. ResNet·DeepAE를 포함한 x86-64 native 7개 모델에서는 map 피크가 호출별 버퍼량과 같고, copy 피크가 호출별 버퍼량과 상수량의 합과 같았다. 해당 실험은 AArch64 게스트 cFS 실험이 아니다. [S1] §2.2·§3.1·§7

따라서 정확한 공백은 **“최종 네 실제 모델의 AArch64 cFS 실행에서 두 적재 경로를 대응시킨 증거가 부족하다”**이다. E54의 네 모델은 무조건 상한으로 승인됐지만 관측된 실행은 map 경로였다. [S3] §5.2·§10

### 2.2 OnAIR

E33의 공식 OnAIR 로더 경로에는 다음 결과가 있다. [S2] §4

| SmartCam 조건 | 결과 | 추론 횟수 |
|---|---|---:|
| 예산이 무조건 상한과 같음 | 허용 | 5 |
| 예산이 무조건 상한보다 1바이트 작음 | 거절 | 0 |
| 명세와 아티팩트 불일치 | 거절 | 0 |

이 증거는 x86-64 호스트의 공식 플러그인 연계에 해당한다. 해당 경로의 HAL peak는 측정하지 않았고, 출력 객체 해제도 미검증이다. 이를 AArch64 OnAIR 또는 OnAIR 메모리 상한 준수 결과로 확대하지 않는다. [S2] §9·§10

## 3. 우선 수행: AArch64 cFS 복사 경로 검증

### 3.1 기호와 측정 범위

| 기호 | 의미 |
|---|---|
| `P` | 명세의 `static_per_call_bytes`, 호출별 버퍼량 |
| `C` | 명세의 `module_resident_constant_bytes`, 복사 분기에서 할당되는 상수량 |
| `Bᵤ = P + C` | 무조건 메모리 요구량 상한 |
| `M` | 실행 전에 부여한 대상 메모리 예산 |
| `H` | 해당 실행에서 관측한 HAL 디바이스 할당 peak |

상한과 관측값은 동일한 HAL 할당 범위에서 비교한다. 모듈 이미지, 런타임 고정비, cFS 전체 메모리까지 포함한 RAM 총량으로 해석하지 않는다. [S1] §1·§2, [S3] §4.1·§4.3

### 3.2 수행 조건

- 대상: ResNet, DeepAE, SmartCam, WGAN의 기존 AArch64 VMFB와 명세.
- 환경: 기존 AArch64 QEMU 게스트 cFS 및 동일 IREE 런타임·드라이버.
- 예산: `M = Bᵤ`로 두고 무조건 상한 기준으로 승인한다.
- 변경 변수: 모듈 적재 주소의 정렬 또는 검증된 매핑 제어 수단.
- 고정 변수: 모델 바이트, 명세, 입력, 컴파일 설정, 출력 판정 기준.
- 모델당 최소 1회 추론을 완료한다. 반복 수는 측정 전에 고정한다.

**조건부 승인 상태에서 정렬을 깨지 않는다.** 현재 cFS 구현은 조건부 승인 후 정렬 전제가 충족되지 않으면 런타임 생성 전에 거절한다. 이를 우회하는 대신 무조건 승인 경로를 사용한다. [S4] `AI_LEARNER_Init`, `g.conditional_map` 정렬 검사

정렬 제어는 모듈 형식의 유효 정렬을 보존해야 한다. E29는 8바이트 배수 오프셋으로 64바이트 정렬 여부를 바꿨으며, 8바이트 배수가 아닌 경우 모듈 검증 실패를 관측했다. AArch64 대상에서도 유효성을 먼저 확인한다. 단순 `malloc` 호출만으로 copy를 강제했다고 가정하지 않는다. 별도 매핑 비활성 옵션의 존재와 의미는 **미검증**이므로 확인 전에는 계획의 전제로 삼지 않는다. [S1] §2.2

### 3.3 수집할 증거

1. VMFB·명세 식별값과 적용된 실행 설정
2. 실제 모듈 주소의 `mod 64`
3. 모듈 append 전후 HAL 할당 통계
4. 추론 전 상수 할당의 잔존량과 추론 후 HAL peak
5. 실행 판정, 완료 횟수, 출력 파일 또는 검증 가능한 출력 기록
6. 기존 순차 호출 계측을 적용할 경우 `max_active_calls`

분기 이름을 출력한 사실만으로 copy를 확정하지 않는다. 적재 설정, 상수 할당 관측, 실행 결과를 함께 대조한다. 이는 본인 분석·판단이다.

### 3.4 완료 기준과 해석

| 확인 대상 | 기준 | 의미 |
|---|---|---|
| 적재 성공 | 유효한 모듈로 append 성공 | 정렬 오류에 의한 모듈 거절과 구분 |
| 상수 복사량 | 기준선과 측정 구간을 맞춘 append 직후 상수 할당량이 `C`와 일치 | `C`의 실행 대응 확인 |
| 실행 완주 | 모델별 추론 1회 이상 완료 | 적재만 확인한 결과와 구분 |
| 상한 유효성 | `H ≤ P+C` | 관측 실행에서 상한 위반 없음 |
| 상한 도달 여부 | `H = P+C`인지 별도로 기록 | 관측 실행에서 상한이 실제 peak에 도달하는지 확인 |
| 출력 보존 | 기존 동일 타깃·동일 모델 출력 기준 충족 | 적재 방식 변경의 계산 영향 확인 |

`H < P+C`이면 상한이 틀렸다는 뜻이 아니다. 정확한 도달 여부와 상한 유효성을 별도로 판정한다. `H > P+C`이면 원자료를 보존하고 원인 분석 전까지 해당 구성의 상한 준수 주장을 보류한다.

네 모델의 한 번씩 관측은 경로별 실행 대응 증거이다. 모든 지원 입력·실행에 대한 건전성은 지원 연산, 버퍼 수명, 상수의 상주 구간과 순차 호출 전제에 대한 분석 근거로 함께 설명해야 한다. 반복 호출의 장기 수명도 이 네 번만으로 검증됐다고 하지 않는다. 이는 본인 분석·판단이다.

## 4. 기존 map 실험과 통합하는 방법

다음 표의 실행 결과는 새로 관측하거나 조건이 일치하는 보관 원자료로 채운다. 기대 결과를 실측 결과로 기입하지 않는다.

| 구성 | 적재 경로 | 예산 | 확인할 결과 |
|---|---|---:|---|
| 무조건 승인·map | map | `Bᵤ` | `H ≤ Bᵤ`, `H=P` 여부 |
| 무조건 승인·copy | copy | `Bᵤ` | `H ≤ Bᵤ`, `H=P+C` 여부 |
| 조건부 승인·map | map | `P` | 전제 충족, 조건부 허용, `H ≤ P` |
| 조건부 정책 비활성 대조 | 추론 미실행 | `P` | `P < Bᵤ`이면 거절·추론 0회 |

기존 E54의 첫 번째 구성과 SmartCam 조건부 결과는 설정·아티팩트·측정 구간이 대응하면 재사용한다. 앱이나 계측 변경이 비교에 영향을 주면 영향받은 셀만 재측정한다. 모든 모델의 모든 셀을 일괄 재실행하는 것을 기본 요구로 삼지 않는다. [S3] §5.2·§10, 본인 분석·판단

DeepAE의 기존 TFLite 대비 수치 동치 FAIL은 유지한다. 같은 AArch64 실행의 map/copy 출력 일치와 원본 TFLite 대비 동치는 별도 비교이다. [S5]

## 5. OnAIR: 기존 결과를 우선 활용

### 5.1 유지할 수 있는 기여

> 명세 기반 실행 전 판정을 공식 OnAIR 플러그인 인터페이스에 연결하고, 허용 및 거절 시의 실행 동작을 실증했다.

이 문장은 E33의 SmartCam 결과와 연결할 수 있다. OnAIR 코어 무수정은 E33 §1·§4, 허용·거절과 추론 횟수는 §4가 뒷받침한다. OnAIR를 포함했다는 이유만으로 HAL peak와 반복 출력 수명 검증까지 필수화할 필요는 없다. [S2], 본인 분석·판단

### 5.2 신규 판정표를 추가할 경우의 범위

네 모델을 한 행씩 정리하고 허용·거절 조건을 모두 비교하면 모델당 두 조건, 총 8조건이다. 이는 보조 보강이며 현재 권고의 필수 추가 실험은 아니다.

| 시험 수준 | 확인하는 것 | 확인하지 않는 것 |
|---|---|---|
| 동일 JSON·예산을 판정 코드에 입력 | 명세 해석과 판정 결과의 일치 | 공식 OnAIR 실행 경로, 메모리 준수 |
| 공식 OnAIR 로더에서 플러그인 시험 | 설정 전달, 판정 적용, 실행 또는 실행 차단 | HAL 상한 및 반복 출력 수명 |
| 반복 실행·HAL 관측·객체 수명 시험 | 해당 배포에서의 메모리 준수 근거 | 전체 시스템 RAM의 자동 보장 |

같은 함수를 두 번 호출한 결과의 일치는 공유 구현의 일관성 확인이다. 독립적인 알고리즘 검증으로 표현하지 않는다. cFS와 OnAIR의 서로 다른 연결 코드까지 확인하려면 실제 연결 지점의 결과를 비교해야 한다. 이는 본인 분석·판단이다.

E33은 x86-64 OnAIR 시험이다. 같은 AArch64 JSON을 사용한 정책 시험과, 타깃에 맞는 명세·VMFB로 수행하는 공식 OnAIR 실행 시험을 구분한다. 서로 다른 ISA의 명세와 VMFB를 섞어 통합 실행 성공으로 보고하지 않는다. [S2] §4·§9

### 5.3 보류할 확대 주장

현재 증거로 OnAIR 경로의 반복 실행 메모리 상한 준수를 주장하지 않는다. 이를 새 기여로 선택할 때에만 HAL peak와 출력 객체 수명을 별도 검증한다. 공식 플러그인 연계 기여를 유지하는 것과 메모리 준수 주장으로 확대하는 것은 다른 결정이다. [S2] §10

## 6. 실행 우선순위 및 종료선

1. 기존 x86-64 copy 증거와 AArch64 map 증거를 구분해 연결한다.
2. 네 모델의 AArch64 cFS copy 경로를 무조건 상한 예산으로 실행한다.
3. 기존 권고의 조건부 map 셀과 통합해 `P`, `C`, `Bᵤ`, `H`를 대응시킨다.
4. 기존 OnAIR E33 허용·거절 결과를 기여와 연결한다.
5. OnAIR 신규 8조건 표는 모델 전반의 판정 재사용을 별도로 주장할 때만 추가한다.

종료선은 **AArch64의 두 적재 경로에 대한 명세–실행 대응을 확보하고, OnAIR 기여를 실제 확보한 연계·판정 증거에 맞추는 것**이다. 실험 횟수, 시간 비용, 성공 결과는 실행 전 추정만으로 확정하지 않는다. 이는 본인 분석·판단이다.
