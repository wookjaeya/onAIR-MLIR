# OnAIR/cFS 정적 메모리 계약 연구 v0.4 검토

- 검토 대상: `REPORT_v0.4.md`, `EVIDENCE_v0.4_E7.md`
- 대상 버전: v0.4, 2026-09-07
- 비교 기준: 이전 `PROGRESS.md` v0.3 검토
- 검토 범위: 보고서와 증거 문서의 정합성, E7·E8의 증거 수준, 주장 범위, 후속 검증 우선순위
- 제한: 실제 파서·판정기 코드와 원자료를 재실행한 검토가 아니다. 수치는 첨부 문서의 보고값이며, 건수·비율·수치 관계만 산술 대조했다. 외부 연구 동향 및 문헌 신규성 평가는 포함하지 않는다.

**1. 종합 판단.** v0.4는 v0.3보다 주장과 증거가 잘 맞아졌다. 메모리 계약 검사기의 제한된 개념검증으로는 진전이 있다. 다만 E7의 ‘240건 오류 0’이 검증하는 범위는 보고서의 중심 주장보다 좁고, 메모리 상한 추출의 정확성에도 확인할 부분이 남아 있다. 현재 판단은 **조건부 진행**이다.

**2. 이전 검토의 반영 상태.** 주요 지적은 상당 부분 반영됐다.

| v0.3에서 지적한 문제 | v0.4의 변화 | 판단 |
| --- | --- | --- |
| 50/50과 실험 조합의 불일치 | 입력 30 + 베이킹 30 = 60으로 정정 | 문서상 해소 |
| H1을 일반적으로 기각 | 현 조건에서 우위 미관측, 예측성 일반화 보류 | 적절 |
| H2의 선택 이점이 불명확 | 논문 주장에서 제외 권고 | 현재 증거에 부합 |
| 가중치·상수의 메모리 귀속 | D2 발견, 상수 720,896B 별도 집계 | 중요한 진전 |
| 계약의 책임 범위 불명확 | per-call 버퍼 + 모듈 상주 상수로 명시 | 부분 메모리 계약으로 범위 확정 |
| H3 판정기 부재 | E7 구현, E8 비적용 경로 추가 | 구현 단계 진전 |
| Python 제거의 이점을 선취 | 후속 가설로 강등 | 적절 |

D2의 발견은 메모리 계약의 핵심 위험이 실행시간 잡음뿐 아니라 ‘무엇을 어느 영역에 집계했는가’에 있음을 보여준다. 계약 범위를 명시한 것과 그 범위의 계산이 모든 지원 조건에서 올바르다는 것은 별개다. 이제 핵심 검증 대상은 후자다.

**3. E7의 240건이 뒷받침하는 범위.** E7의 전체 건수와 판정 합계는 일치한다.

- 전체: `10설정 × 3크기 × 2변형 × 4예산 = 240`
- ACCEPT: `10 × 2 × (4 + 2 + 1) = 140`
- REJECT: `10 × 2 × (0 + 2 + 3) = 100`

그러나 설정과 변형에 관계없이 메모리량이 같으므로, 판정을 좌우한 메모리값은 세 가지다.

| h | bounded_bytes |
| ---: | ---: |
| 256 | 12,332B |
| 4096 | 196,652B |
| 16384 | 786,476B |

세 수치는 모두 `M(h) = 48h + 44`에 정확히 들어맞는다. 이는 보고된 세 점에서 확인되는 관계이며, 다른 모델이나 규모에서도 성립한다는 뜻은 아니다.

현재 E7은 이 세 메모리값을 네 예산과 비교하고, 설정·배치 변형을 바꿔도 판정이 일관적인지 확인한 구조다. 따라서 다음 주장을 뒷받침한다.

> 현재 MLP 계열에서 계약 추출과 예산 비교가 설정·변형에 걸쳐 일관되게 동작했다.

반면 다양한 메모리 수명, 버퍼 재사용, 실행 구조에서 배치 오류를 방지했다는 주장까지 강하게 뒷받침하지는 않는다. **240건이라는 수보다 서로 다른 할당 구조를 몇 종류 다뤘는지가 더 중요하다.** 같은 MLP의 설정 수를 늘리기보다 다른 할당 구조를 추가하는 편이 다음 단계의 증거 가치가 크다.

**4. 상수 메모리의 독립 검증이 필요하다.** E7은 관측값을 ‘HAL 피크 + 상수’로 정의한다. 그러나 상수값을 런타임에서 별도로 확인했는지, 정적 파서가 산출한 값을 다시 더했는지는 두 문서에 명확하지 않다.

같은 정적 상수값을 양쪽에 사용했다면 비교는 다음 구조가 된다.

```text
예측값 = T_IR  + C_IR
관측값 = T_HAL + C_IR

두 값의 일치로 확인되는 관계: T_IR = T_HAL
```

이 경우 **상수 집계 C_IR가 맞는지는 확인되지 않는다.** 상수를 잘못 집계해도 양쪽에 같은 오류가 들어가면 일치한다.

h=16384에서 상수는 전체 bounded_bytes의 약 91.7%다.

```text
720,896 / 786,476 ≈ 0.9166
```

따라서 D2 수정 이후에는 D2와 같은 오류를 현재 검증기가 실제로 잡을 수 있는지 확인해야 한다. 별도 관측 경로가 이미 있다면 해당 근거를 문서에 명시하면 된다. 이 검토는 독립 검증이 없다고 확정하는 것이 아니라, 제공된 문서에서 그 근거가 확인되지 않는다는 지적이다.

상수를 독립적으로 관측하기 어렵다면 계약의 검증 상태를 분리해 기술할 수 있다.

- per-call 버퍼: 정적 계산과 HAL 실측 대조 완료
- 모듈 상수: 정적 집계 및 별도의 검증 근거
- 전체 bounded_bytes: 두 근거를 결합한 값

현재 문서만으로 ‘전체 bounded 영역을 런타임에서 독립 검증했다’는 표현은 이르다.

**5. E8은 안전한 거절 경로의 검증이다.** E8의 직접적인 근거는 크기에 사용된 SSA 값이 정수 상수로 해석되지 않았다는 것이다. 여기서 도출되는 결론은 ‘현재 분석기가 이 모델의 메모리 상한을 계산하지 못했다’이다. 이는 ‘이 모델에는 메모리 상한이 존재하지 않는다’와 다르다.

동적 형상이어도 입력 범위가 제한되면 유한한 상한을 구할 수 있다. SSA 값이 정수 리터럴이 아니더라도 상수 계산이나 범위 분석으로 크기를 알아낼 수 있는 경우가 있다.

| 구분 | 권장 의미 |
| --- | --- |
| 분석 결과 | `UNKNOWN_BOUND`: 현재 분석으로 상한을 확보하지 못함 |
| 배치 정책 | 보장 근거가 없으므로 실행을 허용하지 않음 |

E8의 성과는 **알 수 없는 경우를 허용으로 처리하지 않았다는 것**이다. 이를 위해 수학적으로 더 강한 `UNBOUNDED`라는 명칭을 사용할 필요는 없다. ‘정적 상한이 없는 경우’도 ‘현재 분석으로 정적 상한을 산출하지 못하는 경우’로 바꾸는 편이 정확하다.

**6. REJECT의 의미를 정교하게 정의해야 한다.** 현재 판정기는 `U > B`이면 REJECT를 반환한다. U가 보수적인 상한이고 B가 예산이라면, 이 조건은 실제 실행이 반드시 예산을 초과한다는 뜻은 아니다.

예를 들어 계산한 상한이 100KiB, 실제 필요량이 60KiB, 예산이 80KiB라면 상한만 보고 허용하지 않는 것은 안전한 정책이다. 그러나 실제로 실행 불가능한 것은 아니다.

| 조건 | 뒷받침하는 의미 |
| --- | --- |
| 유효한 상한 ≤ 예산 | 명시한 가정 아래 예산 충족을 보증할 수 있음 |
| 상한 > 예산 | 이 상한으로는 예산 충족을 보증할 수 없음 |
| 유효한 하한 > 예산 | 예산 충족이 불가능하다고 판단할 근거가 있음 |

현재처럼 실측과 계산값이 일치하는 사례에서는 이 구분이 드러나지 않는다. 하지만 향후 보수적 계산을 도입하면 중요해진다.

`pessimistic misprediction`은 계산기 결함일 수도 있지만, 보수적인 상한을 사용한 정상적인 결과일 수도 있다. 향후에는 불필요한 거절률 또는 보수성으로 인한 배치 기회 손실로 분석하는 편이 연구 목적에 맞다. REJECT라는 정책 명칭 자체는 사용할 수 있으나, 이를 실행 불가능성의 증명으로 해석하지 않아야 한다.

**7. ‘slice 합 = 상한’의 정확성을 먼저 확인해야 한다.** 보고서는 lifetime 패킹이 있을 때 slice 합이 실제로 보수적인지 확인하는 것을 후속 작업으로 제시한다. 이는 단순한 성능 확장보다 상한 계산법의 정확성을 결정하는 문제다.

예를 들어 버퍼 두 개의 크기가 각각 1B이고 정렬 때문에 오프셋이 0과 64라면, 두 버퍼를 담는 주소 범위는 최소 65B다. 크기의 합인 2B는 상한이 아니다. 반대로 수명이 겹치지 않는 버퍼들이 같은 공간을 재사용하면 크기를 모두 더한 값은 실제 피크보다 클 수 있다.

- 정렬·패딩을 누락하면 과소 추정할 수 있다.
- 수명에 따른 재사용을 무시하면 과대 추정할 수 있다.

실제 파서가 이를 이미 처리하는지는 문서만으로 확인할 수 없다. 어떤 IR 단계에서 어떤 할당 크기를 읽고, 정렬과 수명을 어떻게 반영하는지 중심 방법론에 포함해야 한다.

다음 검증 사례가 현재 MLP의 설정 확대보다 우선한다.

- 정렬 때문에 빈 공간이 생기는 작은 버퍼
- 수명이 겹치는 버퍼와 겹치지 않는 버퍼
- 여러 dispatch에 걸쳐 유지되는 버퍼
- fusion 전후로 중간 버퍼가 달라지는 모델
- 상수 공유와 중복 저장이 달라지는 아티팩트

이 경우에도 안전한 상한을 계산할 수 있어야 단순한 MLP 크기 계산을 넘어서는 방법론적 기여가 드러난다.

**8. cFS 배치 주장과 현재 구현의 간격.** 옵션 (b)처럼 일부 메모리 영역만 계약 대상으로 삼는 것은 타당하다. 모든 시스템 메모리를 컴파일러가 직접 분석할 필요는 없다.

그러나 해당 예산은 전체 cFS 앱에 사용 가능한 메모리와 구분되어야 한다. 런타임 컨텍스트·스택·파이프 등의 비용을 별도로 확보하고, 남은 영역을 모델 버퍼와 상수의 예산으로 배정한다는 연결이 필요하다.

Native-cFS 경로가 잔여 작업인 현재에는 다음 표현이 적절하다.

> OnAIR의 IREE 추론 아티팩트에 대해, 명시한 모델 데이터·실행 버퍼 영역의 메모리 계약과 예산 판정기를 구현했다.

‘cFS 배치 전 admission을 수행했다’는 표현은 실제 cFS 통합과 예산 연결까지 완료한 것으로 읽힐 수 있다.

또한 `RSS − bounded`로 얻은 약 244KB는 미분류 잔차로 다루는 편이 안전하다. RSS와 정적 할당 바이트는 집계 방식이 다르므로, 잔차 전부를 런타임 컨텍스트의 실제 사용량으로 확정하면 또 다른 귀속 문제가 생길 수 있다.

**9. 후속 작업의 우선순위 권고.** v0.4는 Native-cFS 통합을 첫 번째로 두었다. 현재 확인된 방법론적 위험을 기준으로는 계약 추출기의 핵심 정확성을 좁게 확인한 뒤 통합하는 편이 효율적이다.

1. **상수 집계의 독립 검증 경로 확정:** 전체 bounded 영역 중 무엇이 실측이고 무엇이 정적 계산인지 분리한다.
2. **판정 의미와 경계값 정리:** `UNKNOWN_BOUND`, 보증 불가와 불가능의 구분, `U−1 / U / U+1` 예산에서의 동작을 확인한다.
3. **할당 구조가 다른 소규모 사례로 파서 검증:** 정렬·패딩·재사용·다중 dispatch를 각각 확인한다. 큰 CNN 하나보다 실패 원인을 식별하기 쉬운 사례를 우선한다.
4. **Native-cFS 연결:** 부분 메모리 계약이 실제 앱의 예산 배정과 결합되는 방식을 검증한다.
5. **동일 범위의 대안 비교:** MLIR의 필연성보다 IR 기반 계약 추출이 정확성·지원 범위·검증 비용에서 주는 이점을 평가한다.

보고서가 TFLite Micro의 컴파일 시 아레나 크기 제공을 확정적으로 기술하면서 참고문헌에서는 미검증으로 표시한 부분도 정리해야 한다. 이번 검토에서는 그 외부 주장의 진위를 판단하지 않았다. 대안 비교의 전제로 사용하기 전에 확인이 필요하다.

**10. 현재 판정과 권장 서술.** H1·H2를 제외한 방향 전환은 타당하고, E7·E8은 단순 메모리 측정에서 계약 검사기로 진전했다. 그러나 다음 단계의 성공 기준은 판정 건수를 늘리는 것이 아니라, 현재 계산법이 잘못될 수 있는 할당 구조에서도 과소 추정하지 않는다는 근거를 확보하는 것이다.

진행 보고서의 중심 문장으로 다음을 권고한다.

> 정적 형상·단일 호출 조건의 MLP 아티팩트에서 부분 메모리 계약을 추출하고 예산 판정기를 검증했다. 시험한 조건에서 계산값과 관측값은 일치했으며, 분석 불가능한 모델은 허용하지 않았다. 상수 메모리의 독립 검증, 일반적인 할당 구조에 대한 상한의 정확성, Native-cFS 예산 연결은 후속 검증 대상이다.
