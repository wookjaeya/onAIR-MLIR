## 1. 종합 판단

**본인 분석·판단:** 실제 모델과 실제 입력을 AArch64 cFS에서 실행하는 핵심 실험은 상당히 진전됐다. 이제는 실험 수를 늘리는 것보다, 상한 분석의 적용 조건과 실행 경로를 연결하고 남은 수치 불일치를 해소하는 작업의 우선순위가 높다.

현재 확보된 것은 **특정 컴파일·실행 조건에서 산출한 모델 버퍼 메모리 상한을 앱별 예산과 비교하고, 실행을 허용하거나 차단하는 구조의 실험적 근거**다. 전체 시스템 RAM의 여유량을 보장하는 구조로 해석하지 않는다. [S1 §2–5; S3 §5–6]

| 항목 | 현재 판단 | 근거 |
|---|---|---|
| 공개 실입력 → AArch64 cFS 실행 | 세 모델에서 확보 | S1 §2, S2 |
| 원본 모델 대비 수치 동치 | ResNet·SmartCam 통과, DeepAE 실패 잔존 | S1 §2.1–2.2 |
| IR 할당 내역 → 계약 수치 추적 | 네 모델에서 확보 | S3 §2.1 |
| 분석 전제 위반의 자동 차단 | 원장 도구의 검출은 확인, 실제 계약 생성 경로의 강제 연결은 추가 확인 필요 | S3 §2, S5, S7 |
| OnAIR 출력 버퍼 수명 | 미검증 | S3 §5, S8 |
| 계약·예산·관측값의 회계 경계 | 설명은 명확해짐. 기존 배포 계약과 연결 필요 | S3 §6, S4 |
| 기존 기법과의 차별성 | 비교표는 있으나 원문 대조 미완료 | S9 |

## 2. E48: 실제 입력의 AArch64 cFS 검증

### 2.1 확인한 결과

원본 TFLite 모델을 LiteRT로 실행한 출력을 기준값으로 사용한다. 원소별 판정 기준은 다음과 같으며 E48에서 사후 변경하지 않았다. [S1 서두·§2]

- 절대오차 ≤ `1e-4` **또는** 상대오차 ≤ `1e-5`
- 상대오차 = `|a-b| / max(|a|, |b|, 1e-30)`

| 모델 | 실제 입력 | AArch64 cFS 수치 비교 | 메모리 계약·실행 결과 |
|---|---|---|---|
| ResNet | CIFAR-10 200장 | 위반 0/2,000개 원소 | 승인 시 추론, 예산 미달 시 추론 0 |
| SmartCam | 실제 비행 이미지의 썸네일 19장 | 위반 0/57개 원소 | 동일 |
| DeepAE | 실제 log-mel 34개 창 | 위반 46/21,760개 원소 | 메모리 계약 검증은 통과 |

출처: [S1 §2.1–2.4; S2]. 표의 분모는 비교한 출력 원소 수다. 반복 실행 횟수와 데이터셋 크기를 혼동하지 않는다. SmartCam 썸네일 19장은 별도의 무손실 이미지 집합과 합산하지 않는다. [S3 §4.1]

**본인 분석·판단:** 세 모델에 대해 “실제 입력의 AArch64 cFS 실행 증거가 없다”는 이전 지적은 더 이상 적용되지 않는다. 다만 QEMU 실행 증거이며, 실물 보드 측정으로 바꾸어 표현할 수는 없다. [S1 §0·§5]

### 2.2 E48 전체 PASS의 의미

E48의 전체 목표 달성에는 **DeepAE의 기존 실패가 다른 실행 경로에서도 재현되는지 확인하는 것**이 포함된다. 따라서 전체 PASS를 “세 모델 모두 수치 동치 통과”로 읽으면 안 된다. [S1 §2.1–2.2]

DeepAE는 두 ISA에서 같은 한 입력 창에 허용오차 위반이 발생한다.

- 입력: `normal_id_04_00000043_hist_librosa_w98`
- AArch64: 46개 원소 위반, 최대 절대오차 약 `3.6144e-4`
- x86-64: 94개 원소 위반, 최대 절대오차 약 `6.1893e-4`

**본인 분석·판단:** x86 전용 문제로 보기는 어렵다. 그러나 이 결과만으로 변환기·런타임·특정 연산 중 어느 것이 원인인지 단정할 수 없다. 메모리 계약 결과는 유지하되, 모델 의미 보존 검증은 미완료로 분리해야 한다. [S1 §2.2]

### 2.3 예산 경계 실험의 정확한 해석

| 모델 | 무조건 상한 U (byte) | 승인 실행의 HAL peak (byte) | U−1 예산 |
|---|---:|---:|---|
| ResNet | 618,856 | 309,416 | 거절, 추론 0 |
| DeepAE | 1,069,632 | 6,208 | 거절, 추론 0 |
| SmartCam | 18,222,796 | 9,382,092 | 거절, 추론 0 |

출처: [S1 §2.3–2.5; S2].

세 모델 모두 **무조건 상한으로 승인**받았지만 실행은 **map 분기**를 탔다. 이에 따라 관측 HAL peak는 상수 복사를 포함하는 무조건 상한보다 작다.

**본인 분석·판단:**

- U−1 거절은 계약에 따른 정책 경계를 정확하게 적용한 증거다.
- U−1에서 실제 메모리 부족이 반드시 발생한다는 증거는 아니다.
- 이 결과는 보수적인 상한 기반 admission의 성격과 일치한다.
- 더 작은 예산의 정당한 승인은 map 전제를 충족하는 조건부 정책의 별도 문제다. E48은 조건부 정책을 새로 실험하지 않았다. [S1 §2.4·§5]

## 3. 핵심 검증 세 가지의 상태

### 3.1 상한의 건전성

**확인 사실:** E49 allocation ledger는 네 모델의 IR에서 입력 I, 출력 O, 임시 버퍼 T, 상수 C를 추적해 계약 수치와 대조했다. 네 모델에서 일치하고 미분류 연산은 0이다. [S3 §2.1]

| 모델 | I | O | T | C | I+O+T |
|---|---:|---:|---:|---:|---:|
| ResNet | 12,288 | 40 | 297,088 | 309,440 | 309,416 |
| DeepAE | 2,560 | 2,560 | 1,088 | 1,063,424 | 6,208 |
| SmartCam | 602,112 | 12 | 8,779,968 | 8,840,704 | 9,382,092 |
| WGAN | 602,112 | 602,112 | 130,178,560 | 4,283,648 | 131,382,784 |

단위: byte. 이 원장 표는 각 보관 산출물에 대한 분석이며, WGAN의 AArch64 실행을 의미하지 않는다. [S3 §2.1·§8; S1 §5]

**본인 분석·판단:** 관측 peak와 상한의 비교에 더해, 상한의 구성 근거를 추적할 수 있게 된 점이 중요하다. 다만 같은 layout IR을 읽는 여러 구현의 일치는 공통 입력이나 해석 가정의 오류까지 배제하지 않는다. 지원 범위 전체의 건전성에는 연산·수명·분기와 계산식의 대응 근거가 필요하다. [S3 §2.1]

### 3.2 실행 전제

| 전제 | 현재 근거 | 검토 판단 |
|---|---|---|
| 고정 형상 | 분석 및 계약 처리 결과 | 현재 지원 사례에서 확인 |
| 지원 연산 | 네 모델 entry의 원장 분류 | 보관 사례 근거 확보 |
| 한 번에 한 호출 | 실행 소스의 작업·스레드 생성 호출 조사 | 호출부까지 확인하면 근거 강화 가능 |
| 다음 호출 전 출력 수명 종료 | C 실행기는 release 소스 근거, OnAIR는 미검증 | OnAIR의 반복 호출 보장에 중요 |
| driver 일치 | 계약 선언과 배포 설정 대조 | 검사 경로 존재 |
| 조건부 map 전제 | 정렬·append 후 피크 확인 및 관련 실험 | 기존 증거의 실행환경을 구분해 재사용 |

출처: [S3 §5; S4; S8; S10].

**본인 분석·판단:** 스레드 생성 호출이 없다는 사실만으로 외부 프레임워크가 같은 객체를 동시에 호출하지 않는다는 결론은 나오지 않는다. 실제 호출 경로까지 확인하는 것이 적절하다. 충분한 소스 근거를 제시할 수 있다면 동시 호출 계측을 새로 넣는 것을 의무화하지 않는다.

OnAIR의 `del out`은 Python 참조를 제거하는 코드이며 실제 버퍼 해제의 관측값이 아니다. 종료 시 nanobind 경고 역시 누수의 확정 증거로 취급하지 않는다. 현재 상태는 **출력 메모리 해제 미검증**이다. [S8 설명·실행 코드; S3 §5]

### 3.3 회계 일치

저장소는 다음 값을 구분한다. [S4 `accounting_scope`; S3 §6]

| 값 | 의미 | 해석 |
|---|---|---|
| U | 컴파일 시점에 산출한 버퍼 메모리 상한 | 무조건 분기는 I+O+T+C |
| B | 배포 설정으로 주어진 앱별 예산 | 선언된 예산이며 물리 RAM 예약을 의미하지 않음 |
| H | IREE HAL 할당 통계에서 관측한 피크 | 전체 프로세스 RSS와 다름 |

IREE 런타임 컨텍스트, cFS/OSAL, 태스크 스택, wrapper·파일 로딩 임시 메모리 등 계약 밖 항목을 포함하는 전체 RAM 수용성은 현 계약의 보장 대상과 다르다. [S3 §6; S4]

**확인 사실:** 보관 계약 30개 중 E40의 `analysis_domain` 선언을 포함한 것은 1개이며, 배포에 사용한 세 실물 모델의 기존 계약에는 해당 선언이 없다. [S3 §6; S4]

**본인 분석·판단:** 이 사실만으로 기존 수치나 판정이 무효가 되는 것은 아니다. 기존 계약·배포 설정·실행 코드가 어떤 회계 규칙에 해당하는지 연결하면 된다. 보관 근거를 훼손할 수 있는 소급 재생성보다, 기존 산출물을 보존하고 별도 매핑을 추가하는 방식을 우선한다.

## 4. 코드 대조로 확인한 보완점

### 4.1 D84: 감사 도구의 검출과 계약 발행 차단을 구분

**확인 사실:** 기존 파서는 `stream.resource.*`, `stream.tensor.*` 중심으로 탐색한다. E49 원장은 더 넓은 연산 계열을 탐색하고 entry 안의 `stream.async.*`를 검출한다. 보관 IR 25개에서 마지막 entry print 안의 async 연산은 0개였다. [S3 §2]

확인한 `make_contract.py`에는 E49 원장 호출이 없다. E49 회귀검사는 보관 원장 JSON을 검사하고, 별도 합성 입력으로 async 검출을 확인한다. [S5; S7 `e49_alloc_ledger_cases()`]

**본인 분석·판단:** 현재 모델의 감사 결과와 앞으로 생성할 계약에 대한 자동 강제는 별개의 증거다. 다음을 확인한다.

1. 정상 빌드·계약 생성 절차에서 원장 검사 또는 동등한 전제 검사가 필수로 실행되는가?
2. 위반 시 사용 가능한 정상 계약이 발행되지 않는가?
3. 정상 지원 IR은 계속 통과하는가?

다른 빌드 단계에 이미 강제 경로가 있다면 그 연결을 근거로 제시하면 충분하다. 없다면 생성 전 필수 검사로 연결한다. **현재 코드가 실제로 잘못된 계약을 발행했다고 단정한 지적은 아니다.**

### 4.2 E49의 inference_starts는 실행 관측값이 아님

**확인 사실:** `admission_matrix()`는 실제 정책 함수를 호출하지만, `inference_starts`는 다음과 같이 정책 판정에서 계산한다. [S6]

```python
runs = ap.admitted(got) if err is None else False
```

따라서 8/8 통과는 정책 함수의 기대 판정과 일치한다는 증거이며, 실제 실행기에서 추론이 시작됐다는 관측은 아니다.

**권고 — 본인 분석·판단:**

- 필드명을 `execution_authorized_by_policy` 등으로 바꾸거나 유도값임을 표시한다.
- 실제 추론 시작·차단은 E48 등 실행 로그로 연결한다.
- 조건부 map 전제 실패는 E29b의 기존 실행 증거를 재사용하되 x86-64 결과임을 명시한다.
- E29b에서 관측되지 않은 post-append 검사 발동을 관측한 것처럼 표현하지 않는다. [S10 `not_claimed`]
- 이 구분을 바로잡기 위해 전체 실험을 반복할 필요는 없다.

## 5. 추가 연구의 우선순위와 완료 기준

다음 순위·방법은 **본인 분석·판단**이며, 현재 미해결 근거에 직접 대응하는 작업만 포함한다.

| 순위 | 작업 | 구체적 수행방안 | 완료 기준 | 근거 |
|---|---|---|---|---|
| 1 | 분석 전제 강제 경로 확인 | 실제 계약 생성 호출 경로 추적. 연결이 없다면 전제 검사를 필수 단계로 추가 | 위반 입력은 정상 계약 발행 중단, 지원 입력은 통과 | S3 §2, S5, S7 |
| 2 | DeepAE 불일치 원인 분석 | 실패 입력을 고정하고 변환 전후 및 필요한 중간 출력 비교 | 차이가 처음 발생하는 단계 또는 원인을 근거로 좁힘 | S1 §2.2 |
| 3 | OnAIR 출력 버퍼 수명 확인 | Python·IREE 객체 소유권 경로를 확인하고 필요한 경우 allocator 관측 추가 | 반복 호출 시 버퍼 수명과 상한 전제의 대응 확인 | S8, S3 §5 |
| 4 | 순차 호출 근거 보완 | OnAIR 및 cFS의 실제 호출부까지 추적 | 동일 실행 객체에 대해 호출이 중첩되지 않는다는 근거 | S4 |
| 5 | 기존 계약의 회계 매핑 | 모델·계약·배포 설정·회계 규칙·관측 로그의 연결표 작성 | 각 셀의 U·B·H를 같은 정의로 읽을 수 있음 | S3 §6, S4 |
| 병행 | 기존 기법과의 차별성 검증 | 가까운 선행기법의 원문·공식 구현에서 분석 영역과 판정 시점을 대조 | 검색 요약을 넘는 출처·구절 수준 근거 확보 | S9 |
| 선택 | WGAN AArch64 확장 | 큰 임시 버퍼 특성이 필요할 때 타깃 컴파일·계약·실행 추가 | AArch64 산출물과 실행 관측 연결 | S1 §5, S3 §8 |

### DeepAE 분석 시 유지할 기준

원본 TFLite/LiteRT 출력이라는 기준값과 기존 허용오차를 유지한다. 필요하면 중간 표현 또는 다른 실행 경로를 **원인 분석용**으로 추가할 수 있지만, 이를 원래 기준값의 대체와 혼동하지 않는다. 허용오차 통과 여부와 메모리 상한 충족 여부도 분리한다. [판단 근거: S1 서두·§2.2]

### OnAIR 작업의 우선순위 조건

OnAIR 연계를 인터페이스 호환성·정책 재사용 증거로 한정한다면 버퍼 수명 미검증을 명확히 유지할 수 있다. **OnAIR 반복 실행에서도 같은 메모리 상한을 보장한다고 주장하려면** 버퍼 수명 확인이 높은 우선순위다. [본인 분석·판단; 근거 S8]

## 6. 불필요한 작업 확장을 피하는 지침

다음은 이번 검토의 **작업 범위에 관한 판단**이다.

1. **이전 지적을 자동 승계하지 않는다.** E48로 해소된 실입력 AArch64 공백은 완료로 처리한다.
2. **미검증 항목마다 새 실험을 요구하지 않는다.** 소스 근거·기존 로그·산출물 연결로 충분한지 먼저 판단한다.
3. **실험 통과와 연구 주장 검증을 구분한다.** 정책 함수 시험, 실제 추론 관측, 상한 근거는 각각 역할이 다르다.
4. **모델 추가를 완료 조건으로 삼지 않는다.** WGAN AArch64는 세 모델의 기존 근거로 다루지 못한 특성을 검증할 필요가 있을 때 수행한다.
5. **기존 계약을 무조건 재생성하지 않는다.** 회계 설명과 산출물 매핑으로 해소할 수 있다면 그 방식을 우선한다.
6. **회귀검사 개수를 연구 진척의 대리 지표로 쓰지 않는다.** CI·기록 관리는 유지하되 다음 개발은 핵심 미해결 항목을 우선한다.
7. **전체 시스템 메모리 관리로 범위를 확대하지 않는다.** 현재의 앱별 부분 메모리 계약을 정확히 검증하는 데 집중한다.
8. **검토 제안은 근거에 따라 수용하거나 기각한다.** 같은 우려가 기존 증거로 이미 해소됐다면 추가 구현 대신 해당 증거를 제시한다.
