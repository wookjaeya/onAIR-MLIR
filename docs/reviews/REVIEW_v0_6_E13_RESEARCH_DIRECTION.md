제목 후보: **Compiler-Derived Memory Contracts for AI Deployment in cFS**

한국어: **cFS AI 배치를 위한 컴파일러 기반 메모리 계약**

초록과 본문에서는 계약 대상이 전체 앱 메모리가 아니라 실행 버퍼·상수의 부분 영역임을 명시한다. OnAIR는 프로토타이핑·비교 경로, Native-cFS는 배치 검증 경로로 위치를 구분한다. 제목의 ‘Predictable’, ‘Timing’, ‘Optimal Lowering’은 현재 증거로 뒷받침되지 않는다.

**2. v0.6에서 확인된 진전.** 메모리 계약이 실제 cFS 앱의 초기화 판단으로 연결됐다. 이전의 계약 계산·판정기 개념검증에서, 허용 시 실행하고 거부 시 IREE 초기화를 건너뛰는 경로로 진전했다.

| 항목 | 확인한 근거 | 현재 가능한 주장 |
| --- | --- | --- |
| Native 실행 | `native_learner.c`, 빌드 구성 | Python을 사용하지 않는 추론 실행 경로 구현 |
| cFS 통합 | `ai_learner.c`, 허용 로그 | 실제 SB 메시지 수신으로 추론 호출 |
| 초기화 단계 판정 | 예산 비교가 IREE 생성보다 앞에 위치 | 예산 미충족 시 IREE 초기화 차단 |
| 허용 경로 메모리 | `hal_peak=786476` | 시험한 실행에서 HAL 피크가 계약값과 일치 |
| 거부 경로 | 앱 종료 및 cFS OPERATIONAL 진입 | 해당 거부 상황에서 cFS 기동 유지 |
| D3 수정 | 변경 이력의 post-layout 할당량 적용 | 기존 계산법 오류를 발견·수정했다고 보고됨 |

`summary.json`의 E12 최종 값은 원본 로그와 일치한다. Native 구성에서 상수가 HAL allocator를 통과하고 전체 피크가 계약값과 일치한 점은, 이전 상수 메모리 검증 공백에 대한 추가 근거다. 같은 정적 상수값을 관측값에 다시 더하는 방식보다 강한 증거다.

**3. 최우선 문제 — 계약과 실행 아티팩트의 일치 검사.** cFS 앱의 `CMakeLists.txt`는 계약값을 직접 고정한다.

```text
CONTRACT_BOUNDED_BYTES = 786476
CONTRACT_PER_CALL_BYTES = 65580
CONTRACT_CONST_BYTES = 720896
```

반면 앱은 모델을 `/cf/model.vmfb`에서 별도로 읽는다. 제공된 코드에는 해당 모델이 이 계약의 대상인지 확인하는 절차가 없다. 입력·출력 ABI가 같은 더 큰 모델로 파일만 교체해도 기존의 작은 계약값으로 admission을 통과할 수 있다. 실행 중 `within_contract`는 출력만 하므로 실행 전 차단을 대신하지 못한다.

현재 보장은 ‘올바른 모델과 계약을 외부에서 함께 배치했다는 가정 아래 계약값을 앱 예산과 비교한다’는 조건부 주장이다.

필요한 연결은 다음과 같다.

- 계약에 vmfb 식별값, 입력 형상, 실행 구성 등 유효 조건을 기록한다.
- cFS 빌드에서 계약으로부터 헤더를 자동 생성해 수동 상수 복사를 줄인다.
- 로드할 아티팩트와 계약의 일치를 확인한다.
- 검증한 동일 바이트를 IREE 세션에 전달한다.

우선 검증 사례는 **계약 A를 유지한 채 같은 ABI의 모델 B로 교체했을 때 IREE 초기화 전에 거부하는가**다. 계약은 파일명만으로 식별하지 않는다.

**4. standalone의 계약 비교 지표 오류.** `native_learner.c`에는 다음 비교가 남아 있다.

```c
long peak = (long)st.device_bytes_peak;
int per_call_ok = peak <= CONTRACT_PER_CALL_BYTES;
```

보고된 값대로라면 `786476 <= 65580`은 false다. 상수를 포함한 전체 HAL 피크를 per-call 계약과 비교하고 있다. 따라서 제공된 소스는 `per_call_within_contract=false`를 출력하게 된다.

이는 HAL 피크 자체를 반박하는 문제가 아니라 판정 지표의 경계 불일치다. cFS 앱은 `CONTRACT_BOUNDED_BYTES`와 비교하므로 해당 비교는 맞다.

- 전체 피크는 `CONTRACT_BOUNDED_BYTES`와 비교한다.
- per-call 사용량은 초기화 이후 별도 측정 경계에서 계산한다.
- 요약 JSON에도 실제 검증 boolean을 포함한다.

현재 `summary.json`에는 standalone의 해당 boolean이 없어 소스와 요약 사이의 불일치를 놓치기 쉽다.

**5. 호출당 할당량의 측정 경계.** 두 구현의 `hal_bytes_per_call`은 누적 할당량을 호출 수로 나눈 값이다. 모델 상수와 초기 입력 버퍼의 할당이 섞여 있으므로 정상 상태의 호출당 할당량이 아니다.

E12 로그는 다음 식과 일치한다.

```text
초기 상수 + 재사용 입력 = 720896 + 36 = 720932 B
반복 호출의 중간 버퍼 + 출력 = 65536 + 8 = 65544 B

로그 지표 = (720932 + 65544 × n) / n
n=25: 94381.28 B → 로그 94381.3 B와 일치
```

standalone의 약 65,769B도 초기 비용을 3,200회에 나누면 설명된다. 현재 값은 초기화 비용을 상각한 평균 할당량이다. 정상 상태 할당량은 초기화·워밍업 이후 누적 카운터의 차이로 계산해야 한다. standalone은 `st_before`를 읽지만 결과 계산에 사용하지 않는다.

동시에 존재하는 메모리의 피크와, 한 호출 동안 할당한 바이트의 합도 다른 지표다. 재사용 입력 36B는 피크 경계에 포함되지만 매 호출 새로 할당되지 않는다.

**6. 성공 판정과 실패 시 자원 회수.** `AI_LEARNER_Infer()`는 invoke 실패 후에도 `g.n_infer`를 증가시킨다. 입력 기록·등록·출력 읽기의 일부 반환 상태도 확인하지 않는다. 따라서 `n=25`를 정상 추론 25회와 동일하게 쓰려면 다음을 분리해야 한다.

- 호출 시도 횟수
- 정상 완료 횟수
- 입력·실행·출력 단계별 실패 횟수

앱 초기화 중간 실패와 종료 시 IREE 세션·디바이스·입력 버퍼·모델 blob을 정리하는 경로도 없다. 현재의 예산 거부는 할당 전에 발생하므로 그 경로는 문제가 없지만, 파일 오류나 모델 로드 실패 후 재시작에서는 자원 회수를 검증해야 한다.

현재 E12가 검증한 데이터 경로는 SB 수신→추론 호출→EVS·표준출력 기록이다. 출력값은 임의의 패킷 바이트에서 계산되므로 모델의 임무 판단 정확성을 입증한 실험으로 해석하지 않는다.

**7. 성능·RSS·다른 앱 영향에 관한 표현 수정.**

| 현재 해석 | 검토 결과 및 권장 표현 |
| --- | --- |
| RSS 분해는 결정론적 | RSS는 정수로 기록되지만 결정론적 보장이 아니다. 환경·시점·메모리 상주 상태를 갖는 관측값으로 취급한다. |
| 41.5MB→4.3MB는 Python 제거 효과 | Native 경로의 작은 footprint는 유효한 관측이다. 런타임 최소 구성 변경도 있어 차이 전체를 Python 제거 하나의 인과 효과로 귀속하지 않는다. |
| cFS init delta 1,888KB는 앱 비용 | 프로세스 전체 RSS 차이다. 다른 앱도 초기화 중이며, 두 번째 측정은 SB 파이프 생성 전이다. 앱 전용 비용이나 전체 앱 상한으로 쓰지 않는다. |
| 32.2µs→125µs는 희소 호출·캐시 냉각 때문 | 워밍업 후 중앙값과 cFS 평균값이며 측정 경계도 완전히 같지 않다. 호출 간격과 캐시 상태는 후속 검증할 설명 후보다. |
| 거부 시 cFS·타 앱 무영향 | 해당 상황에서 cFS 기동과 관측한 앱 초기화가 유지됐다. 다른 앱의 기능·응답시간 무영향까지 검증한 것은 아니다. |

양쪽 로그에 HS 시스템 모니터 초기화 오류가 있다. 이를 AI 앱 때문이라고 볼 근거도 없지만, 모든 앱의 정상 동작을 확인했다고 표현할 근거도 없다.

스택·파이프의 설정과 잔차 실측은 부분 예산의 경계를 설명한다. 그러나 IREE allocator에 실제 메모리 한도를 설정하거나, 다른 자원 비용을 보수적으로 확보했다는 증거와는 구분해야 한다. 현재 gate는 cFS 공유 객체·태스크 자체의 모든 할당 이전이 아니라 IREE 초기화 이전에 위치한다.

**8. E13 권고 — LLVM IR/asm 관찰은 적합하다.** 목적은 ‘어셈블리 관찰’ 자체보다 **계약과 최종 생성 코드의 연결 확인**으로 잡는 것이 좋다. 시간 측정 부적격 플랫폼에서도 코드 구조 분석은 진행할 수 있다.

추천 실험명: **E13 — MLIR 메모리 계약과 LLVM IR·최종 실행 코드의 대응 분석**

첫 관찰 대상은 vmfb에 들어가는 추론 커널이다. 현재 `build.sh`는 C wrapper를 GCC로 빌드하므로 wrapper의 asm만으로 IREE가 생성한 연산 코드를 확인할 수는 없다.

| 관찰 대상 | 확인할 질문 |
| --- | --- |
| post-layout IR | 계약값을 만든 할당 구조는 무엇인가? |
| 생성된 LLVM IR | 커널이 버퍼를 어떻게 사용하고 추가 임시 저장을 만드는가? |
| 최종 embedded ELF/asm | 최적화 이후 스택·호출·벡터 연산이 어떻게 구현됐는가? |
| C wrapper·IREE 런타임 | 모델 로드와 HAL 할당은 어느 경계에서 발생하는가? |

E13의 질문은 세 가지로 제한한다.

1. **아티팩트 대응:** 분석한 계약과 실행 코드가 같은 모델·컴파일 설정·vmfb에 속하는가?
2. **메모리 범위:** 커널 스택, 외부 호출, 임시 저장 중 현재 계약 밖에 있는 것은 무엇인가?
3. **코드 생성 차이:** generic/host 설정의 벡터화·루프·FMA·호출 경로는 어떻게 다른가?

현재 논문의 중심에는 두 번째 질문이 가장 직접적이다. LLVM lowering 뒤 스택 사용이 나타나더라도, 스택을 제외한 HAL 계약의 반례라고 즉시 판단해서는 안 된다. 대신 별도로 필요한 자원을 명시한다. 커널에 malloc 호출이 보이지 않는다고 전체 런타임에 동적 할당이 없다고 결론 내리지 않는다.

최소 구성은 현재 h=16384 모델과 E9의 정렬·수명 대표 사례다. 컴파일러·런타임·embedded ELF 조건을 유지하고, 필요할 때만 generic/host 두 설정을 비교한다.

기존 성공한 IREE 컴파일 명령에 다음 옵션을 추가하는 방식으로 시작할 수 있다. 옵션 지원은 고정된 툴체인 버전에서 확인한다.

```text
--iree-hal-dump-executable-files-to=<덤프 디렉터리>
```

산출물은 다음으로 한정한다.

- 계약 산출 IR→LLVM IR→ELF→vmfb의 대응 목록과 식별값
- 커널별 버퍼·스택·외부 호출 대응표
- 계약에 포함된 영역과 제외된 영역의 구분
- 해결하지 못한 항목을 미확인으로 표시한 기록

벡터 명령 수나 asm 명령 수만으로 성능 원인이나 WCET를 확정하지 않는다. E13의 성공 기준은 속도 향상이 아니라 추적 가능한 코드·메모리 근거의 확보다.

**9. 논문 구성과 다음 단계.** 현재는 다음과 같은 시스템·방법론 논문 구성이 적절하다. 문헌상 신규성은 별도의 대안 비교와 문헌 검토가 필요하며, 아래 항목이 이미 신규하다고 확정하는 것은 아니다.

| 논문 구성 | 중심 내용 |
| --- | --- |
| 문제 정의 | 배치할 AI 아티팩트에 대해 어느 메모리 영역을 사전에 판정할 것인가 |
| 방법 | post-layout 계약 추출, 실행 가정, 아티팩트 연결, admission 의미 |
| 정확성 범위 | 지원하는 할당 구조, 상한의 가정, UNKNOWN 처리, 제외 자원 |
| 평가 | 구조별 메모리 검증, 경계값, 계약 불일치, Native-cFS 허용·거부 및 실패 처리 |
| 비교 | 동일 경계의 단순 크기 합산·실측 기반 판단·대안 런타임/계약 방식 중 구현 가능한 기준 |
| 한계 | 시간 축 미검증, 단일 모델·호출 조건, 전체 앱 메모리 및 다중 앱 합성 제외 |

검증할 핵심 주장은 세 가지다.

- 명시한 지원 조건에서 post-layout 분석이 계약 대상 영역을 과소 추정하지 않는다.
- 배치 gate가 유효한 계약을 해당 아티팩트에만 적용하고, 불일치·분석 미확보를 허용으로 처리하지 않는다.
- 동일 계약을 Native-cFS 초기화에 연결해 허용·거부 동작과 실행 중 메모리 관측을 재현할 수 있다.

수정·실험 순서 권고:

1. E11의 전체/per-call 비교와 호출당 할당량 지표를 수정하고 재측정한다.
2. E12에 계약–아티팩트 일치 검사와 추론 성공·실패 계측을 추가한다.
3. 모델 로드 실패·앱 종료 후 자원 회수를 검증한다.
4. E13으로 계약과 최종 코드의 대응 및 제외 메모리를 확인한다.
5. 동일 메모리 경계의 대안 비교로 방법의 실익과 신규성 근거를 보강한다.

H1의 속도 우위나 H2의 최적 lowering 선택을 다시 중심에 놓을 필요는 없다. D1–D3는 올바른 측정·계약 추출이 왜 필요한지 보여주는 동기와 실패 사례로 활용하고, 논문 본문은 실험 진행 연대기보다 최종 방법과 검증 근거를 중심으로 구성한다.

현재 결과에 맞는 중심 문장:

> 부분 메모리 계약을 Native 실행과 cFS 초기화 gate에 연결하고, 시험한 모델에서 허용·거부 경로와 HAL 피크의 일치를 확인했다. 계약–아티팩트 일치, 정확한 계측 경계, 실패 시 자원 회수 및 최종 코드와의 대응을 보완해 배치 방법의 검증 범위를 확장한다.
