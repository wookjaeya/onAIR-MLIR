# OnAIR/cFS MLIR 연구 진행 현황 검토

- 검토 대상: `PROGRESS.md`, 기준 버전 v0.3, 2026-09-07
- 대상 연구: Contract-Guided MLIR Lowering for AI Deployment in NASA OnAIR/cFS
- 검토 근거: 제공된 진행 문서의 실험 요약, 수치, 가설 판정 및 정정 이력
- 검토 범위: 현재 연구의 증거 수준, 주장 타당성, 후속 검증 우선순위
- 제한: 원자료, 하네스, `docs/EVIDENCE_v0.*.md` 및 실제 저장소는 이번 검토에서 확인하지 않았다. 아래 수치는 진행 문서가 보고한 값이며, 독립적으로 재현한 결과가 아니다. 외부 연구 동향과 문헌 신규성 평가는 포함하지 않는다.

**1. 종합 판단.** 현재 연구는 실행 환경과 정정 절차를 갖췄지만, 논문의 중심 주장은 아직 확정되지 않은 단계다. 메모리 계약으로 방향을 옮기는 것은 데이터에 부합한다. 다만 E6의 측정 일치를 정적 보장 및 배치 가능성 입증으로 확대하는 해석은 조정해야 한다.

| 항목 | 문서가 보여주는 성과 | 아직 입증되지 않은 것 |
| --- | --- | --- |
| OnAIR 통합 | 동일 플러그인 인터페이스에서 Python·IREE 경로 구축 | 실제 cFS 메시지 처리 경로의 시간·메모리 영향 |
| H1 성능 개선 | 현 실험에서 compiled 경로의 우위 미관측 | AOT 일반의 성능·예측 가능성에 대한 결론 |
| H2 lowering 선택 | CPU 설정과 실행 모델이 비용에 영향을 줌 | 계약 기반 선택기가 단순한 고정 설정보다 유리함 |
| E6 메모리 | 조사한 조건에서 정적 계산값과 HAL 피크 일치 | 모든 허용 실행에 대한 상한, 전체 배치 메모리 상한 |
| H3 실행 전 판정 | 메모리 판정에 사용할 구성요소 확보 | 배치 허용·거절 판정의 정확성과 실제 실행 검증 |
| 기능 동등성 | 시험한 입력에서 작은 부동소수점 오차 | 모든 허용 입력과 최종 판단에 대한 기능 동등성 |

**2. D1 발견과 정정의 의미.** 가중치를 매 호출 인자로 전달한 결함은 성능 비율뿐 아니라 순위 안정성, Pareto front, 메모리 비용의 귀속을 바꿨다. 초기 결과가 컴파일러의 변환 효과와 호출 경계의 데이터 처리 비용을 혼합해 측정했다는 의미다.

`bytes_per_call`을 의무 기록하고, 기존 결론을 삭제하지 않고 철회 원장으로 남긴 대응은 적절하다. 다만 정정 이후에도 다음 사항은 분명히 해야 한다.

- 가중치 임포트가 실제 복사인지, 매핑 또는 참조 등록인지 확인한다. 임포트라는 표현만으로 물리적 데이터 복사를 가정하지 않는다.
- 모델 로드·초기화 비용과 반복 추론 비용을 분리한다.
- B0와 compiled 경로가 동일한 입력·출력 처리 범위를 측정하는지 명시한다.

비교 명칭도 **‘Python 대 AOT’보다 ‘NumPy/BLAS 기반 플러그인 대 IREE 기반 플러그인’**이 정확하다. B0 역시 주요 수치 연산을 네이티브 BLAS에 맡기므로, 단순한 인터프리터 제거 효과를 비교하는 실험으로 해석하면 안 된다. B0를 강한 베이스라인으로 유지한다는 방침은 타당하다.

**3. H1 판정은 현재 조건으로 제한해야 한다.** 문서는 플랫폼을 `FUNCTIONAL_ONLY`로 분류하고, compiled/B0 비율을 4.14×, 2.73×, 2.22×로 보고한다. 그러나 H1은 tail·variability 개선을 주장하며, 해당 비율이 평균·중앙값·p99 중 어떤 통계량인지 요약 표에는 명시되어 있지 않다.

대표 지연값에서 느리다는 사실과 tail 또는 변동성이 나쁘다는 사실은 서로 다른 주장이다. 또한 시간 측정 부적격 플랫폼에서는 상대 성능 비율의 재현성과 불확실성을 별도로 확인해야 한다.

그렇다고 현재 시간 측정 결과를 전부 폐기할 필요는 없다. 동일 환경에서 반복적으로 관측된 큰 차이는 후속 실험의 방향을 정하는 자료가 된다. 현재 문서에 적합한 판정은 다음과 같다.

> 시험한 모델·구현·플랫폼에서 AOT 경로의 성능 우위는 관측되지 않았다. 시간 예측성에 관한 일반화는 보류한다.

**‘2.2배의 대가로 정적 메모리 보장과 Python 런타임 제거를 얻는다’는 교환은 아직 검증되지 않았다.** Native-cFS 변형이 남아 있으며, 현재 OnAIR 플러그인 경로에서 Python 런타임 제거가 확인된 것은 아니다. Native 경로에서는 성능 비율과 메모리 비용을 다시 측정해야 한다. 한 경로의 성능 비용과 아직 구현되지 않은 다른 경로의 이점을 결합해 교환 관계로 제시하지 않는 것이 맞다.

**4. H2는 선택 문제의 필요성이 미입증된 상태다.** 정정 후 남은 결과는 타깃 CPU 지정의 효과, 실행 모델별 런타임 메모리 차이, host-tuned 군집 내 판별 불가능한 편차다. 다목적 상충은 관측되지 않았다.

이는 설정이 비용에 영향을 준다는 증거다. 하지만 계약을 이용해 설정을 선택해야 한다는 증거와는 다르다. 한 설정이 대부분의 조건에서 가장 좋다면, 복잡한 selector 없이 그 설정을 고정해도 충분할 수 있다.

H2를 지지하려면 다음 관계를 검증해야 한다.

> 예산이나 모델 조건이 바뀌면 적합한 설정도 바뀌며, 계약 기반 선택이 고정 설정보다 배치 성공률 또는 자원 효율을 개선한다.

현재 판정은 ‘부분 지지’보다 **‘설정별 비용 차이는 관측됐으나 계약 기반 선택의 이점은 미입증’**으로 쓰는 편이 정확하다.

다만 **H3에는 반드시 Pareto 상충이 필요한 것은 아니다.** 최적 설정을 고르는 문제와 주어진 아티팩트를 예산 내에서 실행할 수 있는지 판정하는 문제는 독립적이다. H2가 성립하지 않아도 H3는 연구할 수 있다.

**5. E6의 측정 일치와 정적 상한의 보장을 구분해야 한다.** E6의 직접적인 성과는 시험한 설정에서 컴파일 결과로 계산한 메모리량과 HAL이 보고한 런타임 피크가 일치했다는 것이다. 그러나 유한한 시험 사례의 일치만으로 모든 허용 실행에서 상한을 넘지 않는다는 보장이 성립하지는 않는다.

정적 보장의 근거에는 다음 사항이 포함되어야 한다.

- 분석에 포함한 버퍼와 할당의 범위
- 정렬·패딩·버퍼 재사용의 계산 방법
- 허용 입력 형상과 실행 경로
- 동시 호출 및 비동기 dispatch의 허용 여부
- 분석 밖에서 발생하는 할당이 없다는 근거 또는 그 비용의 별도 처리

이 조건 아래 계산식이 상한임을 설명하고, E6는 해당 구현이 실제 런타임과 일치하는지 확인하는 증거로 배치하는 것이 타당하다. 정적 분석과 HAL 측정이 같은 할당 계획을 바탕으로 하는 경우, 두 값의 일치가 어떤 수준의 독립적인 검증인지도 밝혀야 한다.

`tightness 1.000`은 더 줄일 수 없는 최적 메모리 사용량을 뜻하지 않는다. 현재 할당 계획에 대한 예측과 관측이 일치한다는 의미일 수 있다.

문서에는 즉시 설명해야 할 분모 불일치도 있다.

> `10설정 × 3크기 × {입력, 베이킹}`은 60건이지만, 결과는 50/50으로 기재되어 있다.

제외·중복·실패한 조건이 있었는지 또는 표기가 잘못되었는지 밝혀야 한다. 이것이 E6 자체의 오류라는 뜻은 아니지만, 현재 가장 중요한 증거의 검증 범위를 불명확하게 만든다.

**6. 65,580B만으로 전체 배치 가능성을 판단할 수는 없다.** 프로그램 메모리와 런타임 컨텍스트를 분리한 것은 타당하다. 다만 그 분리는 H3가 해결해야 할 남은 문제도 보여준다.

| 메모리 구성요소 | 현재 문서에서의 상태 |
| --- | --- |
| 중간 버퍼 및 I/O | 정적 계산·HAL 대조 제시 |
| 베이킹된 가중치·상수 | 계약 포함 여부 불명확 |
| 실행 코드·아티팩트 매핑 | 포함 여부 불명확 |
| IREE 런타임 컨텍스트 | 실측값 제시; 컴파일러 보장 밖 |
| 호출 스택·스레드 스택 | 포함 여부 불명확 |
| cFS 메시지 버퍼·파이프 | Native 경로 검증 전 |
| 동시 추론 시 중첩 사용량 | 검증 전 |

가중치를 베이킹했다고 해서 메모리 비용이 사라지는 것은 아니다. 호출 인자에서 아티팩트 또는 상수 저장 영역으로 비용 위치가 바뀔 수 있으므로 귀속을 확인해야 한다.

H3가 전체 앱의 배치 가능성을 판정하려면 중복 계산을 피하면서 이 비용들을 결합해야 한다. 반대로 연구 범위를 **‘추론 실행 중 추가로 필요한 버퍼의 정적 계약’**으로 한정할 수도 있다. 이 경우 전체 배치 메모리를 보장한다고 기술하면 안 된다.

현재 우선 결정할 사항은 계약이 책임지는 메모리 경계다. 런타임 컨텍스트 비용을 실측했다고 해서 그 값이 자동으로 보수적인 상한이 되는 것은 아니다.

**7. 기능 동등성의 현재 표현도 한정해야 한다.** `max_abs_diff ≤ 4.05e-6`은 유용한 수치 검증 결과다. 하지만 기능 동등성을 판정하려면 출력 범위, 허용 오차 기준, 시험 입력의 범위를 함께 제시해야 한다.

추론 결과가 임계값 판단에 사용된다면 작은 수치 차이도 경계 부근에서 다른 결정을 만들 수 있다. 다음 세 가지를 구분하는 것이 필요하다.

- 수치 출력의 허용 오차 만족
- 최종 분류·상태 판단의 일치
- 시험하지 않은 입력에 대한 일반화

현재 권장 표현은 **‘시험한 입력·설정에서 지정한 수치 허용 오차를 만족했다’**이다. 문서에 허용 오차 기준이 없다면 그 기준을 먼저 명시해야 한다.

**8. 가설 판정 문구의 수정 권고.** 아래는 원문 판정을 대체하기 위한 검토자의 권고이며, 추가 실험 결과가 아니다.

| 항목 | 원문 판정 | 권고 판정 |
| --- | --- | --- |
| H1 | 기각 | 현 모델·구현·플랫폼에서 성능 우위 미관측; 시간 예측성 일반화 보류 |
| H2 | 부분 지지 | 설정별 비용 차이 관측; 계약 기반 선택의 이점 미입증 |
| H3 | 메모리 축 전제 충족 | 정적 버퍼 계약의 후보 근거 확보; 계약 경계·상한 근거·판정기 검증 필요 |
| E6 | sound & tight | 시험 사례에서 정적 계산값과 HAL 피크 일치; 모든 허용 실행에 대한 보장 근거는 별도 확인 필요 |
| 기능 동등성 | 충족 | 시험 범위 내 수치 일치; 허용 오차 기준 및 최종 판단의 동등성 확인 필요 |
| Python 제거의 교환 | 느려지는 대신 보장·제거 확보 | Native-cFS에서 검증할 후속 가설 |

**9. 잔여 작업의 우선순위 권고.** C1+H3로 연구 중심을 옮긴다면, H2를 살릴 상충 워크로드 탐색보다 다음 순서가 일관된다.

1. **E6의 증거 범위를 정리한다.** 50/60건 불일치, 상한의 가정, 포함·제외 메모리, 검증의 독립성을 명시한다.
2. **Native-cFS 경로에서 메모리 경계를 검증한다.** SB 수신→추론→발행 경로를 구현하고, 해당 추론 경로의 Python 제거와 런타임 비용 감소가 실제로 발생하는지 확인한다.
3. **메모리 계약만 사용하는 최소 admission checker를 구현한다.** 예산과 계약에 따라 허용·거절하고, 허용한 아티팩트가 선언한 경계 안에서 실행되는지 확인한다. 이 단계에는 시간 계약이나 다목적 selector가 필수는 아니다.
4. **일반성과 대안 비교를 검증한다.** 정적 형상의 다중 dispatch·버퍼 재사용 모델로 확장하고, 문서에 제시된 TFLite Micro 등과 같은 경계에서 비교한다. 동적 형상은 이후 단계로 미룰 수 있다.

상충 워크로드 탐색은 H2를 계속 주가설로 유지할 경우에 최우선 작업이다. C1+H3로 전환하면서 H2의 생존 여부에 연구 전체를 묶어둘 필요는 없다. 시간 축은 적격 플랫폼 확보 이후에 별도로 검증한다.

현재 문서만으로 MLIR의 필요성이나 문헌상 신규성은 입증되지 않았다. 메모리 계산을 추출했다는 사실을 넘어, 그 계산을 유효한 배치 계약과 실행 전 판정으로 연결하는 기여가 실제로 성립하는지 확인해야 한다.

**10. 진행 문서에 사용할 수 있는 상태 요약.**

> OnAIR의 IREE 추론 통합과 시험 범위 내 수치 일치를 확보했고, 정적 메모리 계산이 HAL 피크와 일치하는 결과를 얻었다. 성능 우위와 계약 기반 lowering 선택의 이점은 확인되지 않았다. 다음 검증 대상은 메모리 계약의 보장 범위와 이를 이용한 Native-cFS 실행 전 판정이다.
