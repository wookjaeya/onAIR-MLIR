# v0.41 결정 검토 및 OnAIR 메모리 계약 비교 실험안

## 1. 결론

현재 연구 범위를 유지한다면 E38 전체 모델 확장, WGAN 반입, 새 MLIR pass 구현 없이 실험을 마무리할 수 있다. 마지막으로 확인할 것은 조건부 정책의 실제 설정 근거와 E37의 증거 연결·재현 완료 상태다.

추가 실험을 하나 수행한다면, 모델 수를 늘리는 E38보다 **OnAIR 실행 경로에서 메모리 계약의 적용 전제가 유지되는지 검증하는 실험**을 우선 검토할 가치가 있다. 다만 이는 현 연구 완료의 필수 조건이 아니라, 실행기와 계약의 연결에 관한 증거를 보강하는 선택적 실험이다.

이 결론과 실험 설계는 **본인 분석·판단**이다. “OnAIR가 계약을 지키지 못한다”는 결론을 사전에 가정하지 않는다.

## 4. 첨부 결정 문서에서 수정할 부분

### 4.1 조건부 설정은 판정 결과와 독립적으로 확인한다

[D1] §6은 특정 예산에서 NOT_ADMITTED가 나왔으므로 opt-in이 0이었다고 설명한다. 그러나 실험에서 필요한 것은 “설정을 바꾸니 판정이 바뀌었다”는 근거다. 판정 차이로 설정 차이를 추론하면 원인과 결과를 독립적으로 검증하지 못한다. 특히 기존 E36은 빌드 설정 잔류 결함을 기록했다.[S2: D61]

권고 절차는 다음과 같다. **본인 분석·판단**이다.

1. 해당 실행 바이너리에 대응하는 컴파일 명령·빌드 로그·설정 검증 기록에서 opt-in 값을 확인한다.
2. 독립 기록이 있으면 기존 실행 결과에 연결하고 종료한다.
3. 없으면 조건부 승인/비활성 대조 두 셀만 설정 기록과 함께 재실행한다.

설정 파일의 현재 값만 확인하는 것은 당시 바이너리의 설정을 확인한 것과 다르다. 또한 앱 코드가 수정됐다고 모든 과거 실험이 무효가 되는 것은 아니다. 과거 결과는 해당 커밋의 증거로 유지하고, 영향받는 경로만 검증한다.

### 4.2 `allocated == freed`를 보편적인 측정 조건으로 쓰지 않는다

[D1] §4는 이 상태에서 HAL peak를 읽는 절차를 제안한다. 하지만 어떤 할당을 어느 구간에서 비교하는지 정의하지 않았다. 초기화 후 유지하는 모델·세션 버퍼까지 포함하면 전체 할당량과 해제량이 같아야 한다는 조건은 부적절할 수 있다.

측정 설계에서는 초기화 후 기준 할당량, 추론 중 피크, 출력 소비·해제 후의 잔여 할당량을 분리한다. **추론 종료 후 정해진 기준 상태로 돌아오는지**를 확인하고, 지속 객체의 정상적인 메모리를 누적으로 오인하지 않는다. 이는 본인 분석·판단이다.

### 4.3 시간 검증은 “원리적 불가능” 대신 연구 범위로 설명한다

[D1] §9의 FUNCTIONAL_ONLY 환경에서 타당하게 도출되는 결론은 “현재 환경의 시간 측정을 실제 배치 하드웨어의 지연·시간 보증 근거로 사용하지 않는다”는 것이다. 시간 계약 연구 자체가 원리적으로 불가능하다는 뜻은 아니다.

저가 SBC 도입 또한 지연 측정의 기회를 제공할 뿐 시간 보증을 자동으로 성립시키지 않는다. 따라서 제외 이유는 **이번 연구가 메모리 계약을 검증하기 때문**으로 정리한다. 본인 분석·판단이다.

### 4.4 MLIR 관련 결론은 관측 범위를 유지한다

“MLIR 수준이 더 정확한 수치나 더 강한 판정을 주지 않는다”는 일반 문장 대신 다음으로 통일한다.

> 현재 비교한 모델·도구·정책 조건에서는 MLIR 기반 경로와 아티팩트 전용 경로의 수치·판정 차이가 관측되지 않았다.

이는 E35의 동등 결과와 맞는다.[S4] 구현하지 않은 정규 pass의 효과까지 부정하는 근거로 사용하지 않는다. 연구 기여는 “MLIR을 사용했다”는 사실보다 **추출한 부분 메모리 요구량을 실행 전 판정과 연결하고 그 전제와 실행 결과를 검증한 방법**에서 평가한다. 후자는 본인 분석·판단이다.

### 4.5 문서 수치는 간단히 정정한다

[D1] §2의 태그 누락 “12개 버전”과 “32개 버전째”는 집계 기준이 불명확하다. 실제 존재하는 버전 수인지 숫자 범위인지 확인해 통일한다. 이는 문서 정정이며 새 실험 사유가 아니다.

## 5. OnAIR 비교 실험은 어떤 질문을 다뤄야 하는가

### 연구 질문

> 같은 모델·컴파일 산출물·런타임 구성·메모리 계약을 사용했을 때, 공식 OnAIR에 연결한 실행 경로에서도 계약이 가정한 출력 수명과 메모리 상태가 유지되는가?

현재 자료는 종료 시 미해제 객체 경고를 보고한다. E33 §10은 객체 해제를 미검증으로 정정했고, HAL peak를 측정하지 않았다고 명시한다.[S1: §9–10] [D1] §4는 경고 객체 수와 추론 횟수의 대응을 추가로 보고한다. 이것은 후속 측정의 동기이며, 실제 HAL 메모리 누적이나 계약 위반의 입증은 아니다.

**본인 분석·판단:** 이 질문은 E38의 모델 수 확대보다 연구의 중심인 메모리 계약 적용 조건을 직접 시험한다. 다만 추가 비교가 학술적 신규성을 자동으로 보장하는 것은 아니다.

### 사전 가설

- H1: 출력 소비·해제 이후 잔여 할당량이 안정적인 기준값으로 돌아가며 계약 대상 피크가 상한 이하다.
- H2: 현재 출력 처리 경로에서 객체 또는 버퍼 보유가 반복마다 누적되어, 계약이 가정한 수명 조건이 유지되지 않는다.
- H3: 종료 경고가 있어도 계약 대상 HAL 할당의 지속적인 누적은 관측되지 않는다.

가설은 본인 분석·판단이다. H2와 H3를 함께 두어 경고와 실질적인 메모리 누적을 구분한다. 관측 결과는 이 외의 형태도 허용하며, PASS/FAIL에 맞추어 가설을 변경하지 않는다.

## 6. 최소 실험 구성

### 6.1 모델과 환경

SmartCam 하나로 시작한다. 기존 공식 OnAIR 경로와 기준 출력이 있어 프레임워크 연결을 새로 설계할 필요가 적다.[S1] DeepAE·ResNet 추가는 첫 실험에서 다른 출력 구조가 필요한 이유가 드러날 때만 검토한다.

아래 통제 조건은 본인 분석·판단이다.

- 같은 ISA, VMFB, IREE 버전·빌드, HAL 드라이버·할당기, 컴파일 옵션을 사용한다.
- 입력 순서·전처리·출력의 실질적인 소비 방식·동시 실행 수를 고정한다.
- 우선 하나의 무조건 계약을 사용하고 초기화와 순차 추론 구간을 구분한다.
- OnAIR x86-64와 cFS AArch64를 직접 인과 비교하지 않는다. ISA와 런타임 배포가 섞인다.
- 기존 AArch64 cFS 결과는 본 실험의 증거로 유지하고, 새 비교는 실행기 차이를 분리하는 보조 실험으로 둔다.

### 6.2 비교 경로

| 경로 | 목적 | 실행 시점 |
|---|---|---|
| A. IREE Python 직접 호출 | 같은 바인딩·출력 처리에서의 기준 상태 | 최초 비교 |
| B. 공식 OnAIR + 현재 연구 플러그인 | 공식 실행 경로에 연결했을 때 상태가 달라지는지 | 최초 비교 |
| C. 공식 OnAIR + 원인 수정본 | 누적의 원인을 제거하면 현상이 사라지는지 | B의 문제가 재현되고 원인을 특정한 경우에만 |

A에서도 B와 동일한 출력 획득·소비 코드를 최대한 재사용한다. A와 B가 함께 누적되면 OnAIR 고유 현상으로 결론내리지 않는다. C는 먼저 만들지 않으며, 수정된 경로의 출력 동치도 확인한다. 이 구성은 본인 분석·판단이다.

### 6.3 계측 가능성부터 확인한다

현재 OnAIR 경로에서 HAL 통계를 직접 얻을 수 있는지는 이번 검토에서 **미검증**이다. 작은 실행으로 동일한 계약 영역의 current/peak를 관측할 수 있는지 먼저 확인한다.

계측이 불가능하면 RSS만으로 계약 위반 실험을 대체하지 않는다. 결과를 객체 수명 진단으로 제한하거나, 계측 확장의 비용을 별도 판단한다. 단순한 모델 추가 실험처럼 비용을 단정하지 않는다.

## 7. 측정값과 판정 규칙

다음은 제안하는 측정 설계이며 본인 분석·판단이다.

| 측정값 | 의미 |
|---|---|
| 초기화 후 HAL current | 모델·세션 등 지속 할당의 기준 상태 |
| 추론 구간 HAL peak | 해당 구간의 최대 계약 대상 할당량 |
| 출력 소비·참조 해제 후 HAL current | 호출 이후 남는 할당량 |
| 반복 번호별 current 변화 | 잔여 할당이 지속적으로 증가하는지 |
| 계약 상한 초과 최초 반복 번호 | 초과가 있을 때 발생 위치 |
| 전체 출력 비교 | 실행·수명 관리 변경의 계산 의미 보존 |
| RSS·객체 수·종료 경고 | 원인 분석의 보조 자료 |

### 측정상 주의

- 할당기 통계가 요청 바이트, 실제 할당 바이트, 캐시 중 무엇을 세는지 확인한다.
- 계약이 포함하는 영역과 current/peak가 세는 영역을 대응시킨 뒤 수치를 비교한다.
- 피크가 누적 최대값인지, 구간별로 초기화할 수 있는지 기록한다.
- 출력을 검증용으로 보존하는 과정 자체가 디바이스 버퍼나 mapped 객체를 붙들지 않도록 한다. 독립적인 호스트 복사본의 메모리는 별도 영역으로 기록한다.
- 호스트 복사본·런타임 캐시·정상적인 지연 해제를 HAL 누수로 단정하지 않는다.
- 강제 GC를 기본 실행에 몰래 추가하지 않는다. 필요하면 별도 진단 조건으로 분리한다.
- 반복 횟수·워밍업·관측 구간·독립 프로세스 재실행 횟수는 측정 전에 고정한다. 처리량 또는 시간 성능 실험으로 해석하지 않는다.

## 8. 결과별로 주장할 수 있는 것

| 관측 결과 | 해석 | 후속 조치 |
|---|---|---|
| 경고가 있으나 HAL current가 안정적이고 peak가 상한 이내 | 측정한 반복 범위에서 계약 대상 메모리 위반이 관측되지 않음 | 경고와 메모리 준수를 구분해 보고 |
| A·B 모두 유사하게 누적 | 공통 바인딩·출력 소비·계측 방식이 원인 후보 | OnAIR 고유 문제라는 해석 보류 |
| B만 누적되고 C에서 사라짐 | 특정 통합 구현의 객체·버퍼 수명 관리가 원인이라는 증거 강화 | 최소 수정과 동일 출력·동일 조건을 제시 |
| 출력 보유가 계약의 수명 전제를 벗어남 | 해당 실행에는 기존 계약의 적용 조건이 충족되지 않음 | 전제 검증·출력 보유 제한·회계 범위 중 필요한 것을 수정 |
| 계약 전제가 충족되는데 동일 영역의 peak가 상한 초과 | 추출기·회계 범위·실행 모델·계측 중 결함 가능성 | 핵심 주장에 영향을 주므로 원인 확인 필요 |
| 모든 경로가 안정적으로 상한 이내 | 확인한 조건에서 다른 실행 경로에도 계약 적용이 성립 | 실패 사례를 만들기 위한 추가 조건 탐색은 중단 |

위 해석은 본인 분석·판단이다. 상한 초과를 보았다고 곧바로 정적 분석의 건전성 위반이라고 부르지 않는다. 먼저 계약 적용 전제와 회계 영역의 일치를 확인한다. 반대로 전제가 충족된 실제 초과를 단순한 프레임워크 차이로 넘기지도 않는다.

## 9. 결론 표현의 범위

현 연구의 플러그인은 NASA OnAIR의 공식 확장점에 연결한 연구 구현이다.[S1: §1–3] 그 구현의 문제를 OnAIR 전체의 문제로 일반화하지 않는다.

### 결과가 뒷받침하면 사용할 표현

> 고정한 OnAIR·IREE·플러그인 구성에서 반복 추론 후 잔여 HAL 할당의 증가가 관측됐다.

> 출력 수명 관리 변경 후 같은 입력·산출물에서 잔여 할당이 안정화되어, 계약 적용에 출력 수명 조건이 필요함을 확인했다.

> 측정한 반복 범위에서 OnAIR 실행 경로의 계약 대상 피크가 상한 이내로 유지됐다.

위 문장은 결과별 서술 예시이며 현재 확인된 결과가 아니다. “OnAIR는 메모리 계약을 지킬 수 없다”, “NASA OnAIR에 일반적인 메모리 누수가 있다”, “우리 방법만 이를 해결한다”는 주장은 현재 증거가 지지하지 않는다.

## 10. 실행 순서와 종료 기준

### 현재 연구 마무리

1. E37의 증거 연결·재현 완료 보고를 원자료로 확인한다.
2. 조건부 두 셀의 opt-in 설정을 독립 기록과 연결한다. 기록이 없을 때만 두 셀을 재실행한다.
3. 결정 문서의 측정 절차·시간 축 표현·MLIR 관측 범위·태그 수를 정정한다.
4. 기존 범위의 완료 여부를 확정한다. PR·태그는 연구 완료와 별도의 이력 관리로 처리한다.

### 선택적 OnAIR 실험

1. SmartCam으로 HAL 계측 가능성과 계약 영역 대응을 확인한다.
2. 사전 고정한 조건으로 A와 B를 비교한다.
3. 차이가 재현될 때만 원인을 특정하고 C를 추가한다.
4. 상한 준수·전제 위반·계측 한계 중 실제 결과로 종료한다.

**중단 기준:** 동일 영역 계측에 큰 구조 변경이 필요하거나, 새 실험이 전역 메모리 관리·다중 앱·시간 보증으로 확대되면 현 연구의 필수 항목으로 승격하지 않는다. 반면 지원 범위 안에서 실제 계약 초과가 확인되면 해당 주장을 보류하고 원인을 해결한다. 본인 분석·판단이다.

## 11. 적용 원칙

- 검토 제안은 실제 연구 질문과 원자료에 대조한 뒤 채택한다.
- 미실행이라는 이유만으로 모든 셀을 필수로 만들지 않는다.
- 불리한 결과도 유지하고, 사전 결론에 맞춰 기준선이나 측정 조건을 바꾸지 않는다.
- 코드에 존재하는 기능, 실제 실행한 기능, 메모리까지 측정한 기능을 분리한다.
- 주장에는 출처를 붙이고, 미확인 상태는 미검증, 제안은 본인 분석·판단으로 구분한다.
- 향후 원고는 문제·방법·증거의 순서로 쓰며, 검토자 답변처럼 구성하지 않는다.
