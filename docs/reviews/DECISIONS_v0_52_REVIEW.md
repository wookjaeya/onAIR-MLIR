## 1. 종합 결론

`DECISIONS_REQUESTED_v0.52.md`의 방향은 대체로 타당하다. 특히 다음 결정은 현재 연구 범위를 지키는 데 적절하다.

1. OnAIR의 역할을 **인터페이스 호환성과 계약 판정 정책의 재사용 증거**로 한정한다.
2. DeepAE 수치 불일치의 원인을 분석한다.
3. 실물 AArch64 보드, WGAN AArch64, 다중 앱 전역 예산은 현재 연구의 필수 완료 조건에서 제외한다.
4. 보관 계약은 소급 재생성하지 않고 회계 정의와의 연결 관계를 보완한다.

그러나 다음 두 판단은 수정해야 한다.

- **DeepAE만 분석하면 연구가 사실상 완료된다는 판단은 이르다.**  
  상한 분석의 실행 전제와 계약·예산·관측값의 회계 일치도 마무리해야 한다.
- **DeepAE 분석 뒤 논문 초고를 자동으로 시작하는 결정은 기존 지시와 맞지 않는다.**  
  초고는 연구 책임자의 별도 지시 전까지 보류한다.

**본인 분석·판단:** 현 단계의 목표는 실험 수를 최대화하는 것이 아니라, 중심 주장에 직접 필요한 근거를 닫는 것이다. 핵심 완료 조건은 다음 세 가지다.

| 핵심 완료 조건 | 확인할 질문 |
|---|---|
| 상한의 건전성 | MLIR/IREE IR에서 계산한 상한이 지원 범위의 관련 할당을 빠짐없이 포함하는가? |
| 실행 전제의 충족 | 단일 호출, 고정 형상, 지원 연산, 출력 수명, map 조건 등이 실제 배포 경로에서 성립하는가? |
| 회계 일치 | 정적 상한 U, 배포 예산 B, 실행 관측 H가 같은 메모리 영역을 가리키는가? |

## 3. OnAIR 주장 범위

### 3.1 권고 결정

**선택지 (a): OnAIR 연계를 인터페이스 호환성과 정책 재사용 증거로 한정한다.**

문서 근거: A-1은 현재 중심 주장에서 OnAIR를 “호환성 보조 실증”으로 규정하고 있으며, 넓은 주장을 선택하면 IREE Python 바인딩의 객체 수명과 allocator 관측을 새로 다뤄야 한다고 설명한다.

### 3.2 연구 구조에서의 정확한 역할

| 실행 경로 | 현재 입증하려는 역할 |
|---|---|
| cFS AArch64 | 계약 판정과 실제 실행 차단·허용, 같은 회계 영역의 실행 관측 |
| OnAIR | 기존 NASA OnAIR 플러그인 인터페이스 연결 가능성, 동일 계약 정책 재사용 |
| MLIR/IREE 분석 | 모델별 버퍼 메모리 상한과 계약 자료 생성 |

따라서 현재 사용할 수 있는 주장은 다음과 같다.

> MLIR/IREE에서 유도한 메모리 계약 판정 로직을 cFS 실행 경로에 적용하고, OnAIR의 기존 플러그인 인터페이스에서도 같은 정책을 재사용할 수 있다.

다음 주장은 현재 범위를 넘는다.

> OnAIR 반복 실행 전체에서 동일한 메모리 상한을 보장한다.

**본인 분석·판단:** 좁은 범위는 회피가 아니다. cFS는 메모리 계약의 종단 실행 검증을 담당하고 OnAIR는 기존 AI 플랫폼과의 연계성을 담당한다. 두 경로가 서로 다른 연구 질문에 증거를 제공하도록 구분하는 것이 정확하다.

## 4. DeepAE 수치 불일치

### 4.1 현재 상태

문서 근거: A-2의 DeepAE 표.

| 항목 | x86-64 | AArch64 |
|---|---:|---:|
| 허용오차 위반 원소 | 94 / 21,760 | 46 / 21,760 |
| 최대 절대오차 | `6.1893e-4` | `3.6144e-4` |
| 실패 입력 | `normal_id_04_00000043_hist_librosa_w98` | 동일 |
| argmax | 517 | 517 |

기준값은 원본 TFLite 모델의 LiteRT 실행 결과이고, 판정 기준은 원소별 `abs ≤ 1e-4 OR rel ≤ 1e-5`다.

### 4.2 정확한 해석

- DeepAE는 현재 판정 기준에서 **수치 동치에 실패**한다.
- 같은 입력에서 두 ISA 모두 실패하므로 x86-64 전용 현상으로 볼 수 없다.
- AArch64의 오차가 더 작다고 해서 AArch64 결과가 더 정확하다고 단정할 수 없다.
- 이 실패는 모델 메모리 계약의 승인·거절 결과를 무효화하지 않는다.
- 메모리 계약 검증과 모델 의미 보존 검증은 서로 다른 판정 축이다.

### 4.3 수행 권고

**본인 분석·판단:** 다음 순서로 원인을 좁힌다.

1. 실패 입력과 원본 LiteRT 출력을 고정한다.
2. TFLite→IREE 변환 과정에서 수치 결과에 영향을 줄 수 있는 연산을 추출한다.
3. 전체 출력뿐 아니라 가능한 중간 출력 또는 연산 블록의 출력을 비교한다.
4. x86-64와 AArch64에서 최초로 오차가 커지는 위치를 비교한다.
5. 원인을 변환 의미 차이, 연산 구현, 부동소수점 최적화, 입력 전처리 중 하나로 좁힌다.
6. 원인을 확정하지 못하면 검증된 사실과 미확정 원인을 분리해 기록한다.

허용오차는 결과를 통과시키기 위해 변경하지 않는다. 제3의 런타임은 원인 분석용 보조 기준으로 사용할 수 있지만, 단순 다수결로 정답을 결정하는 수단은 아니다.

### 4.4 종료 조건

다음 중 하나를 충족하면 DeepAE 분석을 종료할 수 있다.

- 최초 불일치 단계와 기술적 원인을 재현 가능한 근거로 확인
- 특정 변환 또는 연산 설정으로 불일치를 해소하고, 다른 모델 결과가 유지됨을 확인
- 정해진 분석 범위 안에서 원인을 확정하지 못했음을 증거와 함께 기록하고, 수치 동치 실패를 결과로 유지

완전한 런타임 내부 분석을 무기한 계속하는 것은 완료 조건이 아니다.

## 5. DeepAE 이외에 완료해야 할 핵심 작업

### 5.1 E50의 전제 검사 강제 경로 확인

직전 v0.51.1 검토에서는 E49 allocation ledger가 감사 도구와 회귀검사에는 존재하지만, 실제 `make_contract.py`의 계약 생성 경로에서 필수로 실행되는지는 확인되지 않았다. 첨부 문서는 v0.52에 E50이 반영됐다고만 서술하고 구체적인 해결 내용을 제시하지 않는다.

**본인 분석·판단:** v0.52 저장소에서 다음을 확인한 뒤 이 항목을 완료 처리해야 한다.

- 실제 계약 생성 명령이 지원 연산·비동기 연산·미분류 할당 검사를 호출하는가?
- 전제 위반 시 정상 계약 파일이 발행되지 않는가?
- 정상 지원 모델은 동일한 계약값으로 통과하는가?
- 감사 전용 도구의 통과와 배포 계약 생성의 통과가 혼동되지 않는가?

E50이 이 조건을 충족했다면 추가 구현 없이 근거만 연결하면 된다.

### 5.2 순차 호출 근거

문서 근거: A-2는 `max_in_flight_calls`를 현재 `ARGUED_FROM_SOURCE`로 분류한다.

한 번의 추론 호출에 대한 메모리 상한을 반복 실행에 적용하려면 이전 호출의 출력·임시 버퍼가 다음 호출과 중첩되지 않는다는 전제가 필요하다.

**수행방안 — 본인 분석·판단:**

- cFS AI Learner의 호출 루프와 추론 함수 호출 위치 확인
- OnAIR는 좁은 주장 범위에서 인터페이스 호출 구조까지만 확인
- 동일 실행 객체가 병렬 작업이나 재진입 경로로 호출되는지 조사
- 실행기 내부에서 스레드를 만들지 않는다는 사실과 외부 호출이 순차적이라는 사실을 구분
- 충분한 소스 근거가 있으면 새로운 런타임 계측은 생략

**완료 기준:** 실제 배포 경로에서 한 모델 인스턴스의 추론 호출이 중첩되지 않는다는 근거를 호출부까지 제시한다.

### 5.3 기존 계약의 회계 매핑

문서 근거: A-2는 보관 계약을 재생성하지 않고 회계 매핑을 추가하도록 제안한다.

필요한 매핑은 다음과 같다.

| 항목 | 연결할 대상 |
|---|---|
| 정적 상한 U | 계약 JSON의 `bounded_bytes`, `static_per_call_bytes`, 상수 바이트 |
| 배포 예산 B | cFS macro·override, native argv, OnAIR deployment configuration |
| 관측 H | IREE HAL allocator peak |
| 계약 범위 | 입력·출력·임시 버퍼·모듈 상수 |
| 계약 외부 | IREE 고정 런타임, cFS/OSAL, 태스크 스택, wrapper 및 파일 로딩 임시 메모리 |

**완료 기준:** 각 핵심 실험 셀에서 U·B·H가 어떤 필드와 로그에서 나왔는지 추적 가능하고, 포함·제외 영역이 동일한 정의로 읽힌다.

보관 계약을 소급 재생성할 필요는 없다. 기존 산출물과 현재 회계 정의를 연결하는 별도 표나 sidecar 자료가 적절하다.

## 6. 선행연구 원문 대조

문서 근거: A-2는 TVM USMP, ExecuTorch Memory Planning, TFLM 세 건의 원문 접근이 가능하다고 설명한다.

**본인 분석·판단:** 이 작업은 실험과 병행하되 연구 완료 전에 수행하는 것이 좋다. 구현이 제대로 작동하는 것과 기존 방법과 다른 연구 기여가 있다는 것은 별개의 문제이기 때문이다.

각 선행기법에 대해 다음 축만 검증한다.

| 비교 축 | 확인 질문 |
|---|---|
| 분석 입력 | 모델 그래프, 컴파일러 IR, 최종 바이너리 중 무엇을 분석하는가? |
| 메모리 범위 | 입력·출력·workspace·상수 중 무엇을 포함하는가? |
| 산출물 | arena 계획, 상한, 실제 예약, 최적화 결과 중 무엇을 만드는가? |
| 판정 시점 | 실행 전에 예산과 비교해 실행을 차단하는가? |
| 실행 연계 | 일반 임베디드 런타임 또는 cFS/OnAIR와 연결되는가? |
| 실행 대조 | 정적 수치와 같은 영역의 런타임 관측을 비교하는가? |

검색 요약만으로 “기존 연구가 해결하지 못했다”, “최초다”라고 결론 내리지 않는다. 접근 가능한 원문과 공식 구현에서 직접 확인된 내용만 확정한다.

## 7. 현재 제외해도 되는 작업

### 7.1 OnAIR 출력 버퍼 수명

OnAIR의 역할을 호환성·정책 재사용으로 한정하면 필수 실험에서 제외할 수 있다. 다만 상태는 “해제됨”이나 “누수”가 아니라 **미검증**으로 유지한다.

OnAIR 반복 실행의 메모리 상한까지 연구 주장에 포함할 때만 다음 작업을 수행한다.

- nanobind 객체 수명 분석
- IREE Python 런타임의 allocator 관측
- 반복 호출 사이의 출력 버퍼 잔존 여부 측정

### 7.2 WGAN AArch64

현재 모델군이 검증하지 못하는 큰 임시 버퍼 특성을 AArch64 cFS에서 반드시 확인해야 한다는 연구 질문이 생길 때 수행한다. 모델 수를 늘리기 위한 추가 실험으로는 우선순위가 낮다.

### 7.3 저가 AArch64 SBC

현재 QEMU 결과는 AArch64 기능·계약 검증에 사용할 수 있다. 실물 SBC가 필요한 것은 다음 결과를 주장할 때다.

- 실제 지연과 jitter
- WCET 관련 근거
- 전력과 열
- 실물 메모리 계층 및 OS 스케줄링 영향

첨부 문서의 “시간 축 계약이 원리적으로 불가능하다”는 표현은 다음과 같이 수정하는 것이 정확하다.

> 현재 QEMU 환경의 측정값은 실물 AArch64 배치 대상의 지연·jitter·WCET 근거로 사용하지 않는다.

### 7.4 다중 앱 전역 예산

현재 연구의 `per_app_local_budget`은 개별 앱에 주어진 예산과 모델 계약의 비교다. 여러 cFS 앱의 예산 합계, 동시 활성화, 시스템 잔여 RAM, 전역 예약을 관리하는 문제는 별도의 자원 관리자 연구에 해당한다.

따라서 현재 범위에서는 다음까지만 주장한다.

> 주어진 앱별 예산 안에서 해당 모델 계약의 수용 여부를 실행 전에 판정한다.

## 8. 저장소 운영 항목 평가

### 8.1 PR #3

32개 커밋이 하나의 draft PR에 누적돼 있어 리뷰 단위가 큰 것은 사실이다. CI가 통과하고 충돌이 없다면 병합을 검토할 수 있다.

**본인 분석·판단:** PR 병합은 연구 실험의 선행조건이 아니다. 병합 여부를 DeepAE 분석이나 핵심 검증 착수의 차단 조건으로 두지 않는다. 병합은 저장소 관리 판단으로 처리한다.

### 8.2 태그 정책

“버전 매듭마다 태그”라는 규율과 실제 운영이 v0.9 이후 어긋났다면 다음 중 하나를 명시적으로 선택해야 한다.

- 중요한 공개 기준점에만 태그를 붙이도록 규율 수정
- 실제 버전마다 태그를 관리

**권고 — 본인 분석·판단:** 모든 과거 버전에 소급 태그를 붙이기보다, 현재 운영에 맞게 “외부 인용·릴리스 기준점에 태그”로 규율을 수정하는 편이 합리적이다. 커밋 SHA와 보관 산출물로 과거 결과가 이미 식별된다면 소급 태그의 연구적 이득이 작다.

## 9. 권고 실행 순서

| 단계 | 작업 | 이유 | 종료 조건 |
|---|---|---|---|
| 1 | E50이 분석 전제 검사와 계약 생성 경로를 연결했는지 확인 | 상한 건전성의 실제 적용 여부 결정 | 위반 시 계약 발행 차단 근거 |
| 2 | 순차 호출 근거 보완 | 단일 호출 상한을 배포 실행에 적용하기 위한 전제 | 호출부까지 순차성 확인 |
| 3 | 기존 계약의 회계 매핑 | U·B·H 비교의 의미 확정 | 핵심 셀의 필드·로그·범위 연결 |
| 4 | DeepAE 원인 분석 | 남은 모델 의미 보존 실패 해소 또는 원인 축소 | 원인 확인 또는 근거 있는 미확정 종료 |
| 병행 | 접근 가능한 선행연구 원문 대조 | 기법의 차별성 검증 | 검증 가능한 비교표 작성 |
| 이후 | 연구 상태 최종 점검 | 세 핵심 완료 조건 확인 | 미검증·부분 검증·완료 구분 |
| 별도 지시 후 | 논문 초고 | 기존 연구 책임자 지시 준수 | 별도 착수 지시 |

DeepAE 분석을 먼저 시작해도 연구상 큰 문제는 없다. 다만 DeepAE 분석의 완료만으로 전체 연구 완료를 선언하지 않는다. 1~3단계는 규모가 작더라도 중심 주장의 성립 조건이므로 반드시 확인한다.

## 11. 검토 원칙

후속 결정과 검토에 다음 원칙을 유지한다.

- 기존 검토의 제안을 자동 반영하지 않고 근거와 필요성을 먼저 평가한다.
- 테스트 수와 CI 통과 수를 연구 완성도의 직접 지표로 사용하지 않는다.
- 정책 판정, 실제 추론 실행, 메모리 상한 근거를 서로 다른 증거로 분리한다.
- 미검증 상태는 실패나 성공으로 바꾸어 표현하지 않는다.
- 이미 확보된 로그와 소스 근거로 충분한 항목에는 신규 계측을 요구하지 않는다.
- 연구 범위 밖의 보안·전력·열·인증·다중 앱 전역 관리는 완료 조건에 넣지 않는다.
- 모든 핵심 주장에는 문서명·절·코드·원자료 위치를 연결한다.
- 검토자의 해석은 **본인 분석·판단**으로 명시한다.
