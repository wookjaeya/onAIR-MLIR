# EVIDENCE v0.64 — E58: 적재 분기 결정 요인을 평가 타깃(AArch64 cFS 비행 앱)에서 8 정렬 클래스 전부로 쟀다

**사전 고정 계획**: `docs/plans/E58_alignment_sweep_aarch64.md`(커밋 `4d10203`, **측정 이전**).
**요약 생성기**: `harness/mk_e58_summary.py`(판독기 `stages()`는 `mk_e56_summary`에서 import — E44).
**원자료**: `results/e58_alignment_sweep_aarch64/cells/logs/e58_<model>_off<NN>.log` 32개(게스트 raw log, 앱 자신의 레코드) ·
`scenarios.json` · `summary.json`.
**증거 등급**: 결정론적(앱이 스스로 남긴 HAL allocator 통계·판정 레코드). 게스트는 `FUNCTIONAL_ONLY` — 시간값은 쓰지 않는다.

## 0. 왜

원고 §V.C가 *"적재 분기는 모듈 이미지의 64바이트 정렬이 정한다"*의 근거로 든 것은 E29의 정렬 스윕 64셀과 7모델 쌍 적재였고
**둘 다 x86-64 개발 호스트**였다. 연구 책임자 지시(x86-64는 타깃도 검증 수단도 아니다)로 그 근거는 원고에서 빠져야 했고,
평가 타깃에서 관측된 정렬 클래스는 8개 중 2개(0·8)뿐이었으며 그 둘도 **다른 앱 빌드**에서 나왔다(E55b/D97).

## 1. 셀

4모델(b2_resnet · b3_deepae · smartcam · wgan) × 정렬 오프셋 {0, 8, 16, 24, 32, 40, 48, 56} = **32셀**, 전부 AArch64 게스트 cFS.
**한 모델의 8셀은 같은 바이너리**(E55b 무조건 트리, 커밋 `3e746a8` 소스) — 셀 사이에 바뀐 설정은 앱 자신의 노브
`AI_LEARNER_BLOB_ALIGN_OFFSET` 하나다(0도 명시 설정해 같은 노브 경로를 탄다). 예산 `M = B_u`(런타임 오버라이드, 무조건 ADMIT).
판정은 append 직후·입력 버퍼와 추론 이전의 `map_branch.hal_peak_after_append` 하나로 한다(계획 §3).

## 2. 판정 (계획 §3, 측정 전 고정)

**PASS — 32/32 유효 · D1 성립(제3의 값 0) · D2 성립.** 반증 조건 F1~F4 발동 0건.

| 모델 | `C` | 오프셋 0: append 할당 | 오프셋 8·16·24·32·40·48·56: append 할당 | 제3의 값 |
|---|---:|---:|---:|---:|
| b2_resnet | 309,440 | **0** (map) | **309,440 = `C`** ×7 (copy) | 0 |
| b3_deepae | 1,063,424 | **0** | **1,063,424 = `C`** ×7 | 0 |
| smartcam | 8,840,704 | **0** | **8,840,704 = `C`** ×7 | 0 |
| wgan | 4,283,648 | **0** | **4,283,648 = `C`** ×7 | 0 |

- 32셀 전부 `blob_align.state=applied`·`module_ptr_mod64 == 요청 오프셋`·`ADMIT`·`MATCH`·`map_branch` 존재·
  `allow_conditional_map=0`(V).
- map은 **정확히 오프셋 0에서만**, copy는 **나머지 일곱 클래스 전부**에서 났고, copy의 append 할당은 **정확히 `C`**다 —
  평가 타깃에서 8개 클래스 전부가 관측됐다(이전엔 0·8 두 클래스, 그것도 서로 다른 빌드).
- **한 모델의 8셀은 한 아티팩트·한 바이너리**다 — 각 raw log의 `build_config.contract_artifact_sha256`이 모델당 하나로
  모이고(가드 `e58/4`), 시나리오 파일이 셀마다 같은 `.so`를 지목한다(가드 `e58/4b`). E55b/D97의 *"빌드가 다르다"*
  단서가 이 스윕 안에서는 없다.

## 3. 부수 관측 (판정 아님)

- **같은 바이너리에서 172.30배**: DeepAE는 오프셋 0에서 최종 피크 **6,208 B**(= `P`), 오프셋 8에서 **1,069,632 B**(= `B_u`)였다
  (`final_hal_peak_observed`, 판정에 쓰지 않는 기록 필드). E26f의 *"같은 아티팩트가 배포에 따라 172.30배"*를 **한 앱 빌드 안에서,
  정렬 하나만 바꿔** 평가 타깃에서 보인 셈이다.
- ResNet도 같다 — 오프셋 0 최종 피크 **309,416**(= `P`) · 나머지 일곱 **618,856**(= `B_u`).
- SmartCam 오프셋 8·40 셀과 WGAN 8셀 전부는 90초 창 안에 첫 추론이 끝나지 않아 최종 피크가 없다(`None`) — 계획 §2가
  창을 적재 기록용으로 잡았기 때문이다. 판정은 append 시점만 보므로 영향이 없고, 부재를 값으로 읽지 않는다(D29·D51).
  WGAN의 최종 피크 `P`/`B_u`는 E55b(copy)·E55/E56(map) 셀이 보인다.
- `mem_init.hal_peak`는 append 피크에 입력 버퍼 하나를 더한 값이다(D96 — 같은 최고수위선의 두 시점, 분기를 판별하지 않는다).

## 4. 가드

`harness/contract_negative_tests.py::e58_alignment_sweep_aarch64_cases` — 6건(`e58/1`~`/5`, `/4b`). `e58/5`는 판정을
**게스트 raw log에서 임시 파일로 다시 유도**해 커밋된 summary와 대조한다(D89 — 커밋된 JSON만 읽는 가드는 원자료를

원복하면 통과.

## 5. 원고 반영 (계획 §5)

- §V.C의 *"64 alignment cells"*와 표 `tab:arms`(x86-64 native 7모델)를 이 32셀로 **대체**한다. 합성 5모델 행은 삭제한다.
- 결정 요인의 **기전**(`iree_hal_heap_buffer_wrap()`의 64바이트 정렬 조건)은 여전히 소스 읽기이고, 이 실험은 그 귀결을 평가
  타깃에서 관측한다 — 원고는 둘을 구분해 쓴다.
- x86-64 셀(E29)은 디스크에 남기되 원고의 근거로 인용하지 않는다.

## 6. 주장하지 않는 것

- 다른 드라이버·IREE 릴리스에서 정렬이 유일한 결정 요인이라는 것.
- 최종 실행 피크·출력 동치(이 스윕은 append 시점만 판정한다).
- 8의 배수가 아닌 오프셋의 거동(노브가 거부한다).
- 배포가 copy 분기를 탄다는 것 — 앱은 자기 이미지를 정렬하므로 **구조적으로 map**이고, 이 스윕은 정렬을 **일부러** 제어했다.
