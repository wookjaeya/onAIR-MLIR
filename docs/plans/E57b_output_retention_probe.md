# E57b 계획 — OnAIR 경로에서 출력 버퍼가 호출마다 남는 원인 분리 (진단)

**사전 고정 문서다. 진단 셀을 돌리기 전에 커밋한다.**

## 0. 무엇을 봤는가 (E57 관측, 판정은 E57 요약에서)

E57 실험 B의 첫 두 셀(AArch64 게스트, 공식 OnAIR 로더, 플러그인이 자기 할당자를 `del out` 뒤에 읽음)에서
**호출마다 live 바이트가 정확히 출력 텐서 크기만큼 늘었다** — ResNet +40 B/호출(= `O`), DeepAE +2,560 B/호출
(= `O`). 따라서 피크도 `P + (n−1)·O`로 선형 증가한다. 사전 등록 반증 조건 **F4**(`peak(N) != peak(1)`)가
발동했다. E57 계획은 F4를 *"실패가 아니라 결과"*로 미리 정했다.

플러그인은 호출마다 `y = np.array(out, copy=True)` 후 `del out`을 한다. 파이썬 참조는 놓았는데 디바이스 버퍼가
남는다. E33의 원자료(`nanobind: leaked … HalBufferView·MappedMemory` + `keep_alive records`)와 같은 방향이다.

## 1. 질문

남는 것은 **호스트 읽기(readback) 경로**가 붙드는 것인가, **호출 자체**가 붙드는 것인가.

## 2. 셀 — 게스트, 같은 휠·같은 AArch64 vmfb(DeepAE, `O`=2,560 B가 커서 잘 보인다), OnAIR 없이 20회

| 셀 | 호출 후 처리 |
|---|---|
| R0 | 결과를 읽지 않고 즉시 `del out` |
| R1 | `y = np.array(out, copy=True); del out` (플러그인과 동일) |
| R2 | `y = out.to_host().copy(); del out` |
| R3 | R1 + 매 호출 `gc.collect()` |

셀마다 **별도 프로세스**(HAL 통계는 프로세스 전역, E41 교훈). 호출마다 `device_bytes_live`·`device_bytes_peak`를 기록.

## 3. 해석 규칙 (측정 전 고정)

- R0이 호출 후 append 직후 수준으로 돌아오고 R1이 `O`씩 늘면: **보유는 읽기 경로에서 생긴다.**
- R0도 늘면: 호출 자체(바인딩의 결과 반환)가 보유한다.
- R3가 R1과 다르면: 순환 참조가 원인이고 수집이 풀어 준다.
- 어떤 경우에도 **플러그인을 고치는 것은 이 진단의 범위가 아니다** — 고친 뒤의 셀은 별도 실험으로 사전 등록한다.
  E57의 관측(보유가 일어난다)은 이 진단 결과와 무관하게 그대로 남는다.

## 4. 주장하지 않는 것

- IREE 상류의 결함이라고 단정(이 휠 한 빌드·한 드라이버)
- cFS 경로도 같다고(그 경로는 C 런타임이고 E55가 `max_active_calls`·피크 불변을 관측했다)
