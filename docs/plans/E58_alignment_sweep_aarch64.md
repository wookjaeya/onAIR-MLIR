# E58 계획 — 적재 분기 결정 요인을 평가 타깃(AArch64 cFS 비행 앱)에서 8 정렬 클래스로 측정

**사전 고정 문서다. 측정 이전에 커밋한다.** 이 파일이 커밋된 뒤에 셀을 돌린다.

## 0. 왜 하는가

연구 책임자 지시(2026-09-22): **x86-64는 이 논문의 타깃도 검증 수단도 아니다. 모든 실험과
V&V는 AArch64 기반이어야 한다.**

원고 §V.C가 *"적재 분기는 모듈 이미지의 64바이트 정렬이 정한다"*의 근거로 드는 것은 E29의
**정렬 스윕 64셀**(8모델 × 8 정렬 클래스)과 **7모델 쌍 적재**(표 `tab:arms`)인데, 둘 다
**x86-64 개발 호스트의 프로브·native 실행기**다(`results/e29_conditional_contract/align_sweep.json`,
`native_sweep.jsonl`). 평가 타깃에서 그 결정 요인을 본 셀은 지금 다음이 전부다.

| 정렬 클래스(mod 64) | AArch64 cFS 셀 | 출처 |
|---|---|---|
| 0 | 4모델 × 여러 셀 (append 피크 0, map) | E36b·E37·E48·E53·E55·E56 |
| 8 | 4모델 × 1셀 (append 피크 = C, copy) | E55b |
| 16·24·32·40·48·56 | **없음** | — |

즉 평가 타깃에서는 **8개 클래스 중 2개**만 관측됐고, 그 둘도 **다른 앱 빌드**에서 나왔다(E55b/D97).
*"map ⟺ 64바이트 정렬"*을 평가 타깃의 관측으로 쓰려면 나머지 여섯 클래스가 필요하다.

## 1. 착수 전 조사 (실험 아님, 판정 아님)

- 앱의 정렬 노브 `AI_LEARNER_BLOB_ALIGN_OFFSET`(`native/cfs_app/fsw/src/ai_learner.c`
  `AI_LEARNER_BlobAlignOffset()`)는 **무조건 빌드에서** 0 이상 4096 이하·8의 배수·0이 아닌 64의 배수가
  아닌 값을 적용한다. 따라서 {0, 8, 16, 24, 32, 40, 48, 56}은 전부 **앱 자신의 노브로** 만들 수 있다
  (E29처럼 별도 프로브나 shim이 필요 없다). 8의 배수가 아닌 오프셋은 E29가 x86-64에서
  **모듈 검증 실패**를 관측했고 노브가 거부하므로 이 실험의 범위 밖이다.
- 앱은 append **직전에** `blob_align` 레코드(`requested_offset`·`state`·`module_ptr_mod64`)를,
  append **직후** 입력 버퍼·추론 이전에 `map_branch` 레코드(`hal_peak_after_append`)를 남긴다.
  E29 프로브와 같은 측정 시점이다 — 그 시점엔 상수 블록 외의 HAL 할당이 없다.
- 셀은 E55b가 만든 **무조건 빌드 트리**(`e55b_<model>_copy`, 커밋 `3e746a8` 소스)를 그대로 쓴다.
  **한 모델의 8셀은 같은 바이너리**다 — E55b/D97이 남긴 "빌드가 다르다" 단서가 이 스윕 안에서는 없다.

## 2. 셀 — 4모델 × 8 정렬 클래스 = 32셀, 전부 AArch64 게스트 cFS

| 항목 | 값 |
|---|---|
| 모델 | b2_resnet · b3_deepae · smartcam · wgan (원고의 네 실물 모델) |
| 아티팩트·계약 | 각 모델의 AArch64 vmfb·계약 (E36b·E32·E53, 재컴파일 0) |
| 앱 빌드 | E55b 무조건 트리, `AI_LEARNER_ALLOW_CONDITIONAL_MAP=0` |
| 예산 | `M = B_u` (런타임 오버라이드) — 무조건 ADMIT |
| 변수 | `AI_LEARNER_BLOB_ALIGN_OFFSET` ∈ {0, 8, 16, 24, 32, 40, 48, 56} (0도 **명시 설정**해 같은 노브 경로를 탄다) |
| 창 | 90 s — 판정에 필요한 레코드는 앱 적재 후 1초 안에 찍힌다(E55b WGAN 로그 실측). 추론 수는 판정 대상이 아니다 |
| 입력 | 재생 입력 없음(SB 텔레메트리). 출력 비교는 이 실험의 질문이 아니다 |

## 3. 판정 기준 (측정 전 고정)

셀마다 `blob_align`·`admission`·`binding`·`map_branch` 레코드를 읽는다.

- **V (유효성)**: `blob_align.state == "applied"`이고 `module_ptr_mod64 == requested_offset`,
  `admission.verdict == "ADMIT"`, `binding.verdict == "MATCH"`, `map_branch` 레코드 존재.
  하나라도 어긋나면 그 셀은 **INVALID**이며 D1·D2 어느 쪽으로도 세지 않는다(부재를 값으로 읽지 않는다 — D29·D51).
- **D1 (이분성)**: 유효 셀 전부에서 `hal_peak_after_append ∈ {0, C}`. **제3의 값이 하나라도 나오면
  두 분기 모형이 평가 타깃에서 반증된다.**
- **D2 (결정 요인)**: 유효 셀 전부에서 `hal_peak_after_append == 0 ⟺ module_ptr_mod64 == 0`.
- **전체 PASS** = 32셀 전부 V 성립 ∧ D1 ∧ D2.

## 4. 반증 조건

- **F1**: 제3의 append 피크 값 (D1 위반).
- **F2**: mod64 0에서 `C`, 또는 mod64 ≠ 0에서 0 (D2 위반).
- **F3**: 노브가 적용되지 않았는데(`state != applied` 또는 mod64 불일치) 셀이 판정에 쓰임 — 수집기가 막는다.
- **F4**: 8의 배수 오프셋에서 모듈 적재 실패(`runtime_load_failed` 등) — AArch64가 x86-64와 다르게
  거동한다는 뜻이며 V 위반으로 기록하고 **숨기지 않는다**.

## 5. 원고 반영 (결과가 PASS일 때만)

- §V.C의 *"64 alignment cells"*·표 `tab:arms`(x86-64 native 7모델)를 이 32셀로 **대체**한다.
  합성 5모델 행은 삭제한다(평가 타깃 셀이 없다).
- 결정 요인의 **기전**(`iree_hal_heap_buffer_wrap()`의 64바이트 정렬 조건)은 여전히 **소스 읽기**이고
  이 실험은 그 귀결을 평가 타깃에서 관측할 뿐이다 — 원고는 둘을 구분해 쓴다.
- x86-64 셀은 디스크에 남기되 원고의 근거로 인용하지 않는다(E56 규칙 그대로).

## 6. 주장하지 않는 것

- 다른 드라이버·IREE 릴리스에서 정렬이 유일한 결정 요인이라는 것(이 구성 한정).
- 최종 실행 피크·출력 동치(이 스윕은 append 시점만 본다; 최종 피크 = `P` / `B_u`는 E55b·보관 map 셀이 보인다).
- 8의 배수가 아닌 오프셋의 거동(노브가 거부한다).
- 실제 배포가 copy를 탄다는 것 — 앱은 자기 이미지를 64바이트 정렬로 잡으므로 **구조적으로 map**이고,
  이 스윕은 정렬을 **일부러 제어**한 것이다(E55b §7과 같은 단서).
