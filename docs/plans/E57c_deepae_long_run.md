# E57c 계획 — OnAIR 경로에서 DeepAE를 승인 예산 초과 지점 너머까지 호출 (보증 G의 직접 관측)

**사전 고정 문서다. 셀을 돌리기 전에 커밋한다.** E57 계획(`docs/plans/E57_onair_aarch64.md`)의 실험 B-2
(DeepAE, `B_u`, N ≥ 100)의 **추가 셀**이며, E57 관측을 본 **뒤에** 설계했다는 사실을 여기 적는다.

## 0. 왜

E57 B-2(N=100)에서 live 바이트가 호출마다 정확히 `O` = 2,560 B씩 늘어 피크가 `P + (n−1)·O`였다(F4 발동).
E57b는 그 보유가 **호스트 읽기 경로**에서 생긴다는 것을 보였다(결과를 버리면 live 0, 피크 = `P`).
이 속도라면 `P + (n−1)·O > B_u` ⇔ `n − 1 > C/O = 1,063,424 / 2,560 = 415.4` ⇔ **n ≥ 417**에서 피크가
승인 예산 `B_u` = 1,069,632 B를 넘는다. 지금까지 그것은 **외삽**이다.

## 1. 셀

- 배포 `e57_b3_deepae_Bu_long`: E57 `e57_b3_deepae_Bu`와 **같은** 아티팩트·계약·fixture·예산(`B_u`)·런타임 휠,
  telemetry만 N = **450**행.
- 플러그인은 매 호출 후(`del out` 이후) 자기 할당자를 읽는다(E57 계측 그대로).

## 2. 판정 (측정 전 고정)

- **G1**: 피크가 처음으로 `B_u`를 넘는 호출 번호 `n*`를 기록한다. 예측은 **417**(외삽).
- **G2**: `n*`가 존재하면 E57 계획의 **F5**(피크 > 판정에 쓴 예산)가 이 경로에서 **관측**된다 — 보증 G 위반.
- **G3**: 450회 동안 live 증가분이 매 호출 정확히 `O`인지(선형성). 아니면 그대로 보고한다.
- 예측이 틀리면(예: 증가가 멈추거나 `n*` ≠ 417) **예측이 아니라 관측을 보고한다.**

## 3. 주장하지 않는 것

- 플러그인 수정(보유를 없애는 읽기 방식) — 별도 실험으로 사전 등록한다.
- cFS 경로에 대한 어떤 것(그 경로는 C 런타임, E55 `max_active_calls`·피크 불변).
