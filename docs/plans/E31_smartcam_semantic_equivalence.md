# E31 계획 — SmartCam 원본 의미 보존 (P2) · **사전 고정 기준**

**규율**: 이 문서의 §3(입력·전처리)과 §4(판정 기준)는 **결과를 보기 전에 고정**하고 그대로 커밋한다.
결과를 본 뒤 기준을 넓히지 않는다. 넓혀야 할 이유가 생기면 변경 사실과 사유를 정오표로 남긴다
(E26·E27과 같은 절차).

**출처**: 아홉 번째 외부 검토 `docs/reviews/ONAIR_MLIR_ARCHITECTURE_PLAN_20260910.md` §10 단계 1
("SmartCam P2: 원본 의미 보존")과 §7.3(전처리), §9.3(수치 비교 기준). 그 문서가 **"지금 가장 먼저
착수할 구현"**으로 지목한 것이 이 실험의 산출물(입력 fixture · 원본 출력 oracle · 전체 출력 comparator)이다.

## 1. 질문

> **원본 OPS-SAT SmartCam `model.tflite`와, 이 저장소가 E30에서 변환·컴파일한 IREE 모델이,
> 같은 이미지에 대해 같은 계산을 하는가?**

E30이 답한 것은 *반입 가능성*(TRANSFORM_REQUIRED → GO)이고, **수치 동치는 명시적으로 P2로 남겼다**
(`feasibility_summary.json`의 `condition_7_numeric_equivalence: "NOT DONE -- P2"`). 이 실험이 그 항목이다.

E30이 기록한 **인터페이스 좁힘 둘**이 여기서 실제로 시험된다.
- **레이아웃**: 원본은 NHWC `[1,224,224,3]`, IREE 엔트리는 NCHW `[1,3,224,224]`. 원소 수와 dtype은
  같고 **순서는 다르다** → **전치**(transpose)로 대응한다. `reshape`는 틀린 답을 준다.
- **배치**: 원본 `shape_signature`는 배치를 기호적으로 남겼고 실행 형상은 1이다. 비교는 배치 1에서 한다.

## 2. 무엇을 실행하는가 (경로)

| 경로 | 구현 | 역할 |
|---|---|---|
| **oracle** | `ai_edge_litert` 2.2.0 `Interpreter`, 원본 `model.tflite` 무수정 | 원본 의미의 기준값 |
| **IREE(x86-64)** | E30이 만든 `results/p1_smartcam_feasibility/build/smartcam.vmfb`, pip `iree.runtime`, `local-sync` | 변환 모델 |

**이 실험은 vmfb를 새로 만들지 않는다.** E30이 한 번의 `iree-compile` 호출에서 만들어 보관한 그 vmfb를
그대로 쓴다(작업 규율 7). 계약·헤더도 재생성하지 않는다.

AArch64·cFS·OnAIR 경로는 이 실험의 범위가 아니다(각각 단계 2·단계 3).

## 3. 입력과 전처리 — **측정 전 고정**

### 3.1 원본 전처리 규약 (원본 저장소에서 확인한 값)

`home/exp1000/config.ini`(commit `be09ece`)의 `default.*`:

| 항목 | 값 | 출처 |
|---|---|---|
| `input_height` / `input_width` | 224 / 224 | config.ini:52-53 |
| `input_mean` | 0 | config.ini:54 |
| `input_std` | 255 | config.ini:55 |

원본 분류기는 외부 바이너리(`bin/image_classifier`)에 이 네 값을 넘긴다. 표준 TFLite `label_image` 규약대로
전처리는 `(pixel - input_mean) / input_std`, 즉 **`pixel / 255` → [0,1]** 이다.

**중복 정규화 확인(계획서 §7.3-2)**: 모델 flatbuffer 안에 `MUL`(y=2.0) 1개와 `SUB`(y=1.0) 1개가 있다
(`operator_inventory.json`). 즉 모델이 내부에서 `x*2 − 1`로 [0,1]→[−1,1]을 만든다. 이는 MobileNetV2 계열의
표준 전처리이며, **외부에서 [0,1]까지만 만드는 것이 맞다.** 외부에서 다시 [−1,1]로 만들면 이중 정규화다.

### 3.2 입력 집합 — 실데이터와 합성을 **분리 표기**

| 묶음 | 개수 | 출처 | 표기 규칙 |
|---|---|---|---|
| `real_examples` | **3** | 원본 저장소 `home/exp1000/mocks/pictures/*.png` (2048×1944 RGB) | 실제 예제 이미지. **평가 데이터셋이 아니다** — 촬영 출처·정답 라벨·학습/평가 분리가 보장되지 않는다(검토 §7.2) |
| `synthetic` | **32** | `numpy.random.default_rng(31)` uniform [0,1), `[1,224,224,3]` f32 | 수치 동치 **커버리지 확장 전용**. 실데이터로 표기하지 않는다 |
| `edge` | **2** | 전부 0.0 / 전부 1.0 | 경계 입력 |

합계 **37개 입력**. 실제 이미지가 3장뿐인 것은 공개된 예제가 그것뿐이기 때문이며, 이 사실을 결과에 명시한다
(random을 실데이터로 대체 표기하지 않는다 — 검토 §7.2).

### 3.3 resize (교란 요인의 처리)

예제 이미지는 2048×1944이고 모델 입력은 224×224다. 원본 분류기 바이너리의 resize 구현을 바이트 수준으로
재현하는 것은 이 실험의 질문이 아니다. **두 경로에 정확히 같은 224×224 텐서를 주면 resize 방식은 비교에서
소거된다**(검토 §7.3-3: "동일한 전처리 결과로 TFLite용 NHWC와 IREE용 NCHW 텐서를 만든다").

따라서 resize는 **fixture 생성 시 한 번** 수행하고 방식을 manifest에 기록한다:
`PIL.Image.resize((224,224), Image.BILINEAR)`, RGB 3채널.

**주장하지 않는 것**: 이 resize가 비행 소프트웨어의 resize와 동일하다는 것. 따라서 이 실험의 결과는
*"같은 입력 텐서에 대한 원본 모델과 변환 모델의 동치"*이지, *"비행 파이프라인 전체의 동치"*가 아니다.

### 3.4 레이아웃 대응

fixture는 **하나의 전처리 결과**에서 두 텐서를 만든다.

```
img → resize(224,224) → float32 → /255 → nhwc [1,224,224,3]      (oracle 입력, .npy로 보존)
                                        → transpose(0,3,1,2) → nchw [1,3,224,224]  (IREE 입력, .npy로 보존)
```

`transpose`이며 `reshape`가 아니다. fixture 생성기는 **`nchw.transpose(0,2,3,1)`가 `nhwc`로 되돌아오는지
자기 검사**하고, 되돌아오지 않으면 fixture를 쓰지 않는다.

## 4. 판정 기준 — **측정 전 고정**

### 4.1 원소별 수치 기준 (E25에서 **변경 없이 승계**)

| 쌍 | 기준 |
|---|---|
| oracle(TFLite) ↔ IREE(x86-64) | 원소별 `abs_err <= 1e-4` **또는** `rel_err <= 1e-5` |

`rel_err = |a-b| / max(|a|, |b|, 1e-30)`. 두 기준 중 **하나만** 만족하면 그 원소는 통과.

E25가 고정한 규칙을 그대로 쓴다(검토 §9.3: 바꾸면 변경 사실을 남기라 — 바꾸지 않는다). 원본 TFLite와 IREE는
**서로 다른 실행 구현**이므로 비트 동일을 요구하지 않는다(검토 §9.3-1).

### 4.2 추가 조건

- **argmax 일치**: 37/37 입력에서 일치해야 한다.
- **argmax만으로 판정하지 않는다**(검토 §9.3-4): 위 4.1의 원소별 기준이 **주 기준**이고, argmax는 추가 조건이다.
  argmax가 맞아도 원소별 기준이 깨지면 FAIL이다.
- **전체 출력 비교**: 3개 출력 전부를 비교한다. 요약값만 비교하지 않는다.

### 4.3 PASS 조건

**37개 입력 × 3개 출력 = 111개 원소 전부**가 §4.1을 만족하고, **37/37 argmax가 일치**하면 PASS.
하나라도 깨지면 FAIL이며, **모델을 바꾸거나 출력을 축약하거나 tolerance를 넓히지 않고**
변환·입력 대응을 먼저 조사한다(검토 §10 단계 1 완료 기준).

### 4.4 사전 등록한 실패 시 조사 순서

1. 레이아웃 대응(전치 방향)을 먼저 의심한다 — reshape/transpose 혼동이 가장 흔한 원인이다.
2. 정규화 중복(외부 [0,1] + 내부 Mul/Sub) 여부.
3. resize 결과가 두 경로에서 정말 같은 텐서인지(같은 `.npy`를 쓰므로 구조상 같아야 한다).
4. 그 다음에야 변환 체인(SQUEEZE 확장 포함)을 의심한다.

## 6. 주장하지 않을 것 (미리 적는다)

- **정확도**: 라벨이 맞는지 평가하지 않는다. 예제 이미지 3장은 평가 데이터셋이 아니다.
- **비행 파이프라인 동치**: resize·촬영·압축을 포함한 원본 전체 경로의 동치가 아니다(§3.3).
- **AArch64·cFS·OnAIR**: 이 실험은 x86-64 호스트의 두 경로만 비교한다.
- **다른 모델로의 일반화**: ResNet·DeepAE는 단계 4다.
- **비트 동일**: 요구하지도, 관측되면 일반화하지도 않는다(E25의 교훈).
