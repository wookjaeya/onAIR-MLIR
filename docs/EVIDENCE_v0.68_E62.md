# EVIDENCE v0.68 — E62: OnAIR 플러그인 경로의 출력 버퍼 보유(D103)를 기전까지 재고, 고치고, 강제했다

**사전 고정 계획**: `docs/plans/E62_onair_output_release.md`(커밋 `046a7af`, **셀 실행 이전** — 측정 대상 코드가 같은 커밋에 있다).
**요약 생성기**: `harness/mk_e62_summary.py`(플러그인 자신의 `plugin_records.jsonl` · `onair_integration_check.py`의 `run.json` ·
프로브 JSON · **보관 E57 셀**만 읽는다).
**원자료**: `results/e62_onair_output_release/` — `probe/*.json`(기전·반복 프로브 4) · `cells/<배포>/`(OnAIR 공식 로더 20셀) ·
`guest_run.log`·`guest_run_ctl.log`(게스트 실행 기록) · `run_e62.sh` · `guest_env.txt` · `summary.json`.
**증거 등급**: 결정론적(HAL 할당자 통계, 파이썬 참조 수, 출력 바이트, sha256). 게스트는 `FUNCTIONAL_ONLY` — 시간값은 쓰지 않는다.
**실행 환경**: AArch64 QEMU 시스템 게스트(Ubuntu 24.04, Python 3.12.3, numpy 2.3.5), `iree-base-runtime 3.11.0` cp312-abi3
aarch64 휠 — **E57과 같은 휠·아티팩트·fixture·텔레메트리·예산**.

## 0. 왜

E57(v0.66)이 평가 타깃의 OnAIR 경로에서 **호출마다 출력 디바이스 버퍼가 하나씩 남는 것**을 관측했고(D103), DeepAE는
450회 실행의 417번째 호출에서 승인 예산을 넘었다(E57c). E57b는 보유를 호스트 readback으로 국한했다. v19 원고 메타리뷰 A의
M1은 *"플러그인에 강제 단계를 추가하라"*, B의 R1은 *"판정의 이전과 전제의 충족을 구분하라"*였다.

## 1. 판정 — **PASS** (P1~P9 전부 성립, 반증 조건 F1~F6 발동 0)

### P1 — 기전 (OnAIR 없이, DeepAE, 모드마다 별도 프로세스)

| 모드 | `MappedMemory` 참조 수: 전 → 생존 중 → 삭제 후 | 모든 참조를 놓고 GC 후 live | 출력 sha256 |
|---|---|---:|---|
| `asarray`(DeviceArray가 하는 그대로) | 2 → 3 → **3** (**+1**) | **2,560 B = `O`** | 5f52d5bb… |
| 버퍼 프로토콜(`memoryview`) | 2 → 3 → **2** (**0**) | **0** | 5f52d5bb… (동일) |

계획 §1이 소스에서 읽은 기전 — `numpy_interop.cc::SimpleNewFromData`의 `PyBuffer_FillInfo`가 올린 참조를
`PyMemoryView_FromBuffer`가 빌린 참조로 취급해 **아무도 내리지 않는다** — 의 귀결이 **측정으로** 확인됐다: 배열이 사라져도
매핑 객체의 참조가 하나 남고, 그 매핑이 버퍼를 붙든다. 소스 해석 자체(어느 줄이 원인인가)는 여전히 **소스 읽기**다.

### P2 — 반복 프로브 (생산 함수 `readback.read_output`, 20회)

`asarray`는 호출 k 후 live **= k × 2,560**(20회 뒤 51,200 · 피크 54,848), 버퍼 프로토콜은 **20행 전부 live 0 · 피크 6,208 = `P`**.
호출별 출력 sha256 **20/20 동일**.

### P3·P4 — 수정 팔 (OnAIR 공식 로더, `output_readback = buffer_protocol`)

| 셀 | 추론 | 모든 호출: 피크 = `P`, live = append 직후(0) | 최대 피크 | 승인 예산 초과 | 출력 = E57 (호출별 비트 동일) | 종료 시 누수 보고 |
|---|---:|---|---:|---|---:|---|
| ResNet | 50 | ✔ | 309,416 | 없음 | 50/50 | 0 |
| DeepAE | 100 | ✔ | 6,208 | 없음 | 100/100 | 0 |
| SmartCam | 50 | ✔ | 9,382,092 | 없음 | 50/50 | 0 |
| WGAN | 3 | ✔ | 131,382,784 | 없음 | 3/3 | 0 |
| **DeepAE 450회** | **450** | ✔ | **6,208** | **없음** | 450/450 | 0 |

**E57c가 417번째 호출에서 승인 예산을 넘었던 바로 그 텔레메트리에서, 450회 전부 피크가 정확히 `P`였다.**

### P5 — 대조 팔 (`output_readback = asarray`, 같은 E62 빌드)

네 모델 전부 호출별 `device_bytes_peak`·`device_bytes_live` 시계열이 **E57 보관 레코드와 정확히 같다**(마지막 행: ResNet
311,376 / 2,000 · DeepAE 259,648 / 256,000 · SmartCam 9,382,680 / 600 · WGAN 132,587,008 / 1,806,336). 출력도 호출별 비트 동일.
대조 팔이 E57을 재현하므로 **수정 팔과의 차이는 배포 키 하나(`output_readback`)에 귀속된다**(F3 불발).

### P6 — 인터프리터 종료 보고

수정 팔 5셀: nanobind 누수 보고 **없음**(0). 대조 팔: E57과 같이 `leaked 2N instances`·`N keep_alive records`
(ResNet 100/50 · DeepAE 200/100 · SmartCam 100/50 · WGAN 6/3), `MappedMemory` 타입이 목록에 있다.
**D51**: 수정 팔의 보고 부재를 *"누수 없음"*으로 읽는 근거는 **같은 하네스·같은 게스트**의 대조 팔이 stderr를 실제로 수집해
보고를 싣고 있다는 것이다(`stderr_capture_demonstrated_by_control: true`) — 수집이 안 된 것과 보고가 없는 것을 구분한다.

### P7 — 기본값

키 없는 ResNet 셀: init 레코드 `output_readback = buffer_protocol`, 50회 전부 피크 = `P`·live 0, 출력 E57과 50/50 비트 동일.

### P8 — 판정 반쪽 불변

`B_u − 1` 네 셀 전부 `NOT_ADMITTED`·`runtime_created: false`(직접 레코드)·추론 0. OnAIR 코어 추적 파일 변경 **0**(20셀 전부).

### P9 — 강제(`enforce_output_release`)

| 모델 | 대조(`asarray` + 강제) | 수정(버퍼 프로토콜 + 강제) |
|---|---|---|
| ResNet | 추론 **1** → `precondition_violated`(live **40** / append 직후 0) → 정지, 최대 피크 309,416, rc 0 | 50회, 위반 0 |
| DeepAE | 추론 **1** → 위반(live **2,560** / 0) → 정지, 최대 피크 6,208, rc 0 | 100회, 위반 0 |
| SmartCam | 추론 **1** → 위반(live **12** / 0) → 정지, 최대 피크 9,382,092, rc 0 | 50회, 위반 0 |

강제 검사는 **첫 호출 직후에** 위반을 잡아 두 번째 출력이 쌓이기 전에 멈췄고(유형 A 없음), 정직한 실행은 한 번도 막지 않았다
(유형 B 없음). **WGAN 강제 셀은 실행하지 않았다**(계획 §3 — 모델 일반성은 세 모델로 한정해 적는다).

## 2. 실행 기록 — 계획과 다르게 한 것 하나

두 WGAN 셀(수정·대조)은 게스트에서 셀당 약 1.5~2.7시간이 걸린다. 계획 §3은 셀 순서를 정하지 않았고, 순차 루프가 수정 셀을
돌리는 동안 **대조 셀을 별도 프로세스로 병렬 시작**했다(`guest_run_ctl.log`, 06:08:35 시작). 순차 루프는 대조 셀을 두 번
돌리지 않도록 그 시점에 멈췄다(그래서 `guest_run.log`에 `== done` 줄이 없다). 판정량은 **프로세스마다 따로인** HAL 할당자
통계이고 대조 셀의 시계열은 E57과 **정확히** 같았으므로(P5) 병렬 실행이 값에 닿지 않았다는 것이 셀 자신으로 확인된다.
시간값은 어디에도 쓰지 않는다.

## 3. 가드

`harness/contract_negative_tests.py::e62_onair_output_release_cases` — 11건. `e62/11`은 판정·기준 전체를 플러그인 레코드·
프로브 JSON·보관 E57 셀에서 **임시 파일로 다시 유도**해 커밋된 summary와 대조한다(D89). `e62/9`·`e62/10`은 기본값(버퍼 프로토콜,
강제 off)과 E57 배포 9개의 `asarray` 고정을 소스·설정에서 읽는다 — 기본값이 바뀌어도, E57 재현이 깨져도 조용히 지나가지 않는다.
**revert-and-confirm-fail**: DeepAE 450회 셀의 417번째 호출 레코드에 live 2,560 B를 심으면 `e62/11`이 실제로 FAIL, 원복하면 통과.

## 4. 원장 조치 (D103)

D103은 철회하지 않는다 — 조치 칸에 E62를 적는다. 이전 readback의 관측(E57·E57c)은 그대로 참이고, E62는 **같은 휠에서** 그
원인을 측정하고 다른 readback으로 전제를 회복했으며 전제 위반을 검출·정지하는 강제 단계를 더했다.

## 5. 원고 반영 (계획 §6 보고 규칙)

- §V.H는 **두 관측을 함께** 쓴다 — 이전 readback의 보유와 417번째 호출 초과(**지우지 않는다**), 그리고 버퍼 프로토콜 readback
  에서 모든 호출이 정확히 `P`였다는 것, 강제 검사가 이전 readback을 첫 호출 뒤에 멈췄다는 것.
- §IV.C·§I 기여 2: 두 통합 지점이 공유하는 것은 **예산 비교와 런타임 생성 전 거부**이고, 실행 전제의 유지·강제는 **경로마다
  따로**다(메타리뷰 B R1.2, A M1.3).
- §VI.C: 이 결과는 표 4의 파이썬 런타임 패키지와 쓰인 두 readback 인터페이스에 대한 것이다.

## 6. 주장하지 않는 것

- IREE 상류 결함의 확정·보고·수정 · 다른 휠·리비전·드라이버로의 일반화.
- 호스트 매핑이 안 되는 결과(디바이스 복사 경로 — 수정 경로는 **거부**하고 조용히 `asarray`로 되돌아가지 않는다).
- WGAN에서의 강제 검사(실행하지 않음) · 지연 · cFS 경로(무관, E55 `max_active_calls`=1) · 조건부 계층(전 셀 off) ·
  프로세스 RSS(D78 — 판정량은 HAL 할당자 통계).
- `_buffer_view`는 고정한 휠(3.11.0)의 **비공개 속성**이다 — 이름이 바뀌면 수정 경로는 거부한다(`ReadbackUnavailable`).
