# EVIDENCE v0.63 — E60: DeepAE 수치 불일치의 층별 위치를 평가 타깃(AArch64)에서 다시 쟀다

**사전 고정 계획**: `docs/plans/E60_deepae_layers_aarch64.md`(커밋 `623df3b`, **셀 실행 이전**).
**도구**: `harness/e60_deepae_layers_aarch64.py`(신규 — 층 분해·참조·E25 규칙은 전부 `e52_deepae_layers`에서 **import**, E44).
**원자료**: `results/e60_deepae_layers_aarch64/guest/guest_outputs.json`(게스트가 낸 층 출력 10개, 26,507 B,
sha256 `1845b328…`) · `guest/build.json`(진단 모듈 10개의 sha256·컴파일 플래그) · `layers.json`(판정).
**증거 등급**: 결정론적(원소별 수치 비교·해시). 게스트는 `FUNCTIONAL_ONLY`이며 시간값은 쓰지 않는다.

## 0. 왜

원고 §V.G는 DeepAE의 허용오차 초과를 *"x86-64 층별 분해로 누산 순서에 국한했다"*(E52)고 적었다. 연구 책임자 지시
(**x86-64는 이 논문의 타깃도 검증 수단도 아니다**)로 그 분해는 원고에서 빠졌고, 원고는 *"평가 타깃에서 층이나 기전으로
국한하지 않았다"*로 바뀌었다. 이 실험은 **층별 위치**를 평가 타깃에서 다시 잰다. 기전은 다루지 않는다 — AArch64에서는
FMA가 기본 ISA라 E52의 *"FMA를 끈 재컴파일"* 대조가 같은 방식으로 성립하지 않는다(계획 §0).

## 1. 무엇을 돌렸는가

| 단계 | 어디서 | 무엇 |
|---|---|---|
| build | 지상 측 컴파일러 | 배치 AArch64 MLIR(`results/e36b_aarch64_models/b3_deepae/b3_deepae.mlir`, E52가 분해한 파일과 sha256 동일 `e40c75d8…`)을 층 경계마다 자른 **진단 모듈 10개**를 `aarch64-unknown-linux-gnu`/`cortex-a53`으로 컴파일. 배치 계약을 만드는 컴파일이 아니므로 one-invocation 규율 대상이 아니다(E52와 같다) |
| run | **평가 타깃**(AArch64 QEMU 시스템 게스트) | 게스트의 IREE 3.11 aarch64 휠로 10개 모듈을 실패 창 하나(`normal_id_04_00000043_hist_librosa_w98`, E45 매니페스트 sha256 `024c8300…`와 대조 후에만 사용)에 실행 |
| compare | 지상 측 | 층 출력을 (i) 원본 TFLite 런타임의 중간 텐서(원고 전체의 기준값, E52의 보존 실행 검사 포함), (ii) float32 순차 누산 참조, (iii) float64 참조와 **E25 규칙**(원소별 `abs ≤ 1e-4` OR `rel ≤ 1e-5`, 무변경 승계)으로 대조 |

입력 바이트는 E45 규칙대로 반입하지 않는다(배포자가 재배포를 거부). 게스트 출력은 모델 출력이지 입력이 아니므로 보관한다
(E48이 같은 창의 최종 출력을 이미 보관한 선례).

## 3. 읽는 법

- **첫 층부터 순차 누산과 다르다**(층 0 worst abs 2.86e-06). 그러나 허용오차를 넘는 것은 층 6·7에서 각 1원소이고, 대량 초과는
  ReLU가 없어 출력이 dB 규모가 되는 **마지막 층**에서만 일어난다.
- 마지막 층에서 목표 출력은 **세 보조 축 전부와** 허용오차 밖이다(기준값 46 · 순차 f32 30 · float64 19). 어느 축도 다수결의
  표가 아니다 — **제3의 기준값은 없다**(E52 §4.3과 같다).
- E52(x86-64)와 **같은 위치**다: L1 = 6, 대량 = 9. 다른 것은 수 — 마지막 층 위반이 x86-64 94 · AArch64 46이고, x86-64 출력은
  순차 f32와 비트 동일했으나 AArch64는 어느 층에서도 그렇지 않다. 원고는 계획 §3대로 **AArch64 값만** 쓴다.

**보조(판정 아님, 계획 §3이 원고 사용을 금지)**: E52의 식 그대로 잰 성장비 — 누적 오차(층 0→9 worst abs) **36.1배**,
유효 문턱 `max(1e-4, 1e-5·median|v|)` **2.46배**. E52의 x86-64 값은 51.9배 / 2.46배였다. *"누적이 문턱 상승을 앞지른다"*는
관측은 두 타깃에서 같은 방향이지만 **원고에 쓰지 않는다** — 계획이 V·L1~L3만 허용했다.

## 4. 가드

`harness/contract_negative_tests.py::e60_deepae_layers_aarch64_cases` — 8건.

- 허용오차가 E25 그대로인지(도구 상수와 기록 양쪽).
- `layers.json`이 **보관된 게스트 출력을 sha256으로 지목**하는지.
- **V를 원자료에서 다시 유도**한다 — 보관 게스트 출력의 마지막 층을 E48 보관 출력과 비트 대조(입력 불필요, numpy만 필요).
  커밋된 `layers.json`만 읽는 가드는 원자료가 되돌려져도 초록이다(D89).
- L1·L2·위반 벡터·L3·보존 실행 검사·보조 성장비의 *"판정 아님"* 표지.
- 층 비교의 **라이브 재실행**은 입력이 필요하므로 E52와 똑같이 `E52_INPUTS`로 게이트한다(없으면 사유를 적은 SKIP).
  이 컨테이너에서 `E52_INPUTS`를 주고 돌려 층별로 일치함을 확인했다.

**revert-and-confirm-fail**: 보관 게스트 출력의 마지막 층 한 원소에 1e-3을 더하면 해시 가드와 V 가드 **2건이 실제로 FAIL**,
원복하면 통과.

## 5. 주장하지 않는 것

- **기전**(FMA·벡터화·축약 순서) — 디스어셈블하지 않았다. *"누산 순서 때문이다"*는 이 실험으로 **쓸 수 없다**. 쓸 수 있는 것은
  *"평가 타깃의 출력은 어느 층에서도 순차 누산과 비트 동일하지 않고, 허용오차 초과는 층 6에서 처음 나타나 마지막 층에서 대량이
  된다"*까지다.
- 제3의 기준값 — float64·순차 참조는 보조 축이다.
- 여러 창 — 실패 창 **하나**다.
- 기준값 생성 위치 — 원본 TFLite 런타임의 중간·최종 텐서는 **지상 측에서** 계산했다. 원고 전체의 기준값(oracle)이 같은
  방식이며, 이것은 평가 대상이 아니라 **기준값 생성기**다.
