## 0. 왜 했는가

연구 책임자 지시(2026-09-22): x86-64는 이 논문의 타깃도 검증 수단도 아니다. 원고 §VI.A의 근거였던
E35는 4구성 중 **3개가 x86-64**였고, E27의 드리프트 아티팩트는 **x86-64**였다(`elf.json` arch `x86_64`).

## 2. Part B — 컴파일러 드리프트 (AArch64 재컴파일 8회, 모델당 한 번의 호출 × 2리비전)

같은 네 입력 MLIR(sha256이 계약의 `provenance.mlir_sha256`과 **4/4 일치**)을 두 리비전으로 **같은 명령**으로
`aarch64-unknown-linux-gnu`/`cortex-a53`에 컴파일했다.

- **대조(3.11.0rc20260316 @ e4a3b04)**: 네 모델 전부 보관 계약의 세 수치를 **재현**(4/4). vmfb 바이트는
  보관본과 다르다 — E26e가 기록한 스레딩 비재현성이며 수치는 같다. 이 대조가 있어서 드리프트 셀의 차이를
  *"명령이 달라서"*가 아니라 *"컴파일러가 달라서"*로 읽을 수 있다.
- **드리프트(3.10.0rc20260107 @ ae97779)**: PyPI `iree-base-compiler==3.10.0`이 보고하는 리비전이며
  **E27 x86-64 드리프트 아티팩트와 같은 리비전**이다.

|---|---|---|---:|---|
| b2_resnet | **618,856** (3.11과 동일) + note | per_call **12,288** = 입력만 · `unresolved=[]` | 12,328 | 거부 `C4_DISASM` |

- (c)의 note와 (b′)의 거부 사유는 같은 문자열이다: `iree-dump-module`이 *"bytecode version mismatch; runtime
  supports 17.0, module has 16.0"*으로 디스어셈블을 거부한다.
- (b)는 그 디스어셈블에서 `hal.device.queue.alloca`를 읽는데, 읽지 못한 것을 **없는 것으로** 적어 입력 텐서
  하나만 남긴 per_call을 내고 `unresolved=[]`를 보고한다. 네 값 전부 **버전과 무관한 하한 I+O보다 작다** —
  같은 인터페이스를 가진 어떤 컴파일도 입력과 출력을 동시에 쥐어야 하므로 이 값은 **불가능**하다.
  3.11 값과 다르다는 것은 판정 근거로 쓰지 않았다(계획 §3 — E27 자신이 3.10의 정답이 3.11과 같다고 단정할
  근거가 없다고 적었다).

**판정 B: (c) value 4 · (b) impossible_value 4 · (b′) explicit_refusal 4 · tool_error 0.**

## 3. 원고에 미치는 것

- §VI.A의 *"정상 조건에서 두 수준이 일치"*는 이제 **네 AArch64 아티팩트**에서의 관측이다(4/4).
- *"드리프트 아티팩트에서 한 아티팩트 전용 분석기가 조용히 틀린 값을 냈다"*는 E27의 **n=1(합성 MLP, x86-64)**에서
  **n=4(원고의 네 실물 모델, AArch64)**로 바뀐다. 굳힌 분석기가 사유와 함께 거부하고 layout 기반 분석이 수치 + note를
  남긴다는 대비도 같다.
- 넓어지지 않은 것: **리비전은 여전히 하나**다(3.10). *"리비전 전반에 걸쳐 특성화했다"*고 쓰지 않는다.

## 4. 수집기 자신의 결함 (판정 전 수정)

첫 실행에서 (b′) 셀의 사유가 `refusals=None`으로 기록됐다 — 굳힌 분석기는 사유를 `refusal_code`·`refusal`에 싣는데
수집기가 존재하지 않는 키를 읽었다. 분류(`explicit_refusal`)는 맞았지만 **사유를 읽지 못한 거부를 사유 없는 거부로
적은 것**이고, 이 저장소가 D51에서 이름 붙인 형태(볼 수 없었다 ↔ 보았더니 없더라)의 작은 판본이다. 키를 고치고
Part B 전체를 다시 돌렸다(재실행 결과 판정 불변, 사유 문자열만 채워짐).
