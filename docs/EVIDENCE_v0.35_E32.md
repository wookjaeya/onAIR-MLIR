## 0. 한 줄 요약

E31이 x86-64에서 확인한 **원본 의미 보존이 AArch64 native·cFS 양쪽에서 유지**됐고(사전 고정 기준,
전체 출력), 예산 경계 판정도 계약대로 동작했다. 그러나 **조건부 승인 계층에서 사후 검증이 승인 근거가
아닌 값과 비교하고 있었다**(D59) — 계획서 §4.3의 Q3이 그 셀에서 **미달**이며, 그것이 이 실험의 가장
값진 산출이다.

## 1. 계약과 헤더 — 그리고 그 앞을 막고 있던 것 (D58)

한 번의 `iree-compile` 호출(`aarch64-unknown-linux-gnu` / `cortex-a53`)에서 vmfb·덤프·layout IR을
만들고 계약·헤더를 생성했다. 입력 MLIR은 E30이 만든 것과 **sha256 동일**(`f1f659fa…`)이므로 두 타깃의
차이는 삼중항뿐이다.

| 항목 | x86-64 (E30) | AArch64 (E32) |
|---|---:|---:|
| `bounded` | 18,222,796 | **18,222,796** |
| `per_call` | 9,382,092 | **9,382,092** |
| `constants` | 8,840,704 | **8,840,704** |
| dispatch | 56 | 56 |
| 커널 스택 | 439 B (호출 38, 전부 해석) | **1,919 B (호출 0)** |
| vmfb | 8,915,257 B `aa95a6f5…` | 8,991,281 B `ecffe6e0…` |

**계약 세 수치가 ISA에 무관하게 같다**(이 구성의 관측이며 일반 증명이 아니다 — E14 이래 같은 성질).
오버라이드 **0개**, `constants_confirmation_state: confirmed`, 구조적 추출기 일치, artifact-only
hardened 기준선도 같은 세 수치.

### D58 — 헤더 생성기가 정직한 모델을 거부하고 있었다 (유형 B 과잉 거부)

첫 시도에서 `gen_contract_header.py`가 거부했다: 40개 dispatch 중 5개가
`bucket_4_unaccounted_dynamic_stack`. x86-64에서 같은 모델은 `bucket_2`였다.

원인은 LLVM의 **과정렬 프레임**이다. 64바이트 정렬 지역 버퍼가 필요한 dispatch는 이렇게 나온다.

```
stp d15, d14, [sp, #-160]!      ; callee saves
sub x9, sp, #0x6a0              ; 상수 즉치 1696
and sp, x9, #0xff..c0           ; 내림 정렬 → 추가 감소는 최대 63 B
add x29, sp, #0x40
...
sub sp, x29, #0x40              ; 한 번에 재정렬 전 sp로 복귀
```

`elf_stack_frame.py`는 **프롤로그 쪽을 E14부터 인식했고 올바른 상한(160 + 1696 + 63 = 1919)까지
계산해 두고 있었다.** 복귀는 `mov sp, x29`만 인식해 오프셋 철자에서 `realign_restored`가 거짓으로
남았고, 그것이 `dynamic_stack_alloc`을 세워 bucket (4)로 보냈다. **x86-64의 같은 관용구
(`lea -N(%rbp),%rsp`)는 E14부터 처리하고 있었고 주석에 "AArch64 `mov sp, x29`의 대응물"이라고
적어두기까지 했다** — 빠진 것은 AArch64의 오프셋 철자 하나뿐이었다. D47과 같은 구조다: **도구가 맞는
수치를 계산해 놓고 자기가 쓰지 못하게 막고 있었다.**

수정은 한 방향으로만 작동한다(거부 → 해소, 역방향 없음): 에필로그 `sub sp, x29, #K`는 프롤로그의
`add x29, sp, #K`와 **K가 같을 때만** 복귀로 인정한다.

**독립 검증(논증이 아니라 산술)**: `all_dispatch_frames_balanced`가 `false` → **`true`**로 바뀌었다.
이 필드는 차변(`frame_bytes`)과 대변(`restore_bytes`)을 **따로 누적해** 대조하므로, "패턴이 맞았다"와
다른 진술이다. 40개 dispatch 전부 균형이며, 13개가 이 관용구를 쓰고 그중 **5개가 새로 인식된 철자**다.

회귀 10건(수용 2 + 거부 4 + 보관 산출물 4). **revert-and-confirm-fail**: 새 인식기만 되돌리면 수용
2건이 실제로 FAIL하고 거부 4건은 그대로 통과한다. 보관 14개 계약 **diff 0**.

## 2. 의미 동치 — 판정 PASS

기준은 **E25 → E31에서 변경 없이 승계**(원소별 `abs<=1e-4` **OR** `rel<=1e-5`), 기준값은 **원본
TFLite oracle**(E31이 LiteRT로 만든 것을 그대로 사용, 다시 돌리지 않았다), 판정 도구도 E31의
`harness/e31_compare.py` 그대로다.

| 셀 | 경로 | 샘플 | 원소 | 실패 | argmax | 최악 abs | 판정 |
|---|---|---:|---:|---:|---|---:|---|
| **S-native** | native C, AArch64, qemu-user | 37 | 111 | **0** | 37/37 | 1.252e-06 | **PASS** |
| **S-cfs** | cFS `AI_LEARNER`, AArch64 게스트 | 5 | 15 | **0** | 5/5 | 1.252e-06 | **PASS** |

S-cfs의 5개는 **계획서가 측정 전에 고정한 셀 정의**(실이미지 3 + 경계 2)이며 결과를 보고 줄인 것이
아니다. E31이 실증한 대로 상수 경계 입력만으로는 레이아웃 오류를 잡을 수 없으므로 **비상수 실이미지
3개를 전부 포함**한다. 37개 전부의 대조는 S-native가 담당한다.

부수 관측: 두 AArch64 경로의 출력이 5샘플 전부 **비트 동일**이었다. 같은 vmfb·같은 런타임 구성이므로
놀랍지 않지만, **일반화하지 않는다**(E25의 cross-ISA 비트 동일을 일반화하지 않은 것과 같은 이유).

## 3. 예산 판정 — 계약대로 동작

native AArch64(예산이 argv라 런타임 값):

| 예산 | 판정 | 추론 |
|---:|---|---:|
| `B−1` = 18,222,795 | **NOT_ADMITTED** | 0 |
| `B` = 18,222,796 | ADMIT | 완주 |
| `B+1` = 18,222,797 | ADMIT | 완주 |

cFS 게스트(`B+1`, 무조건 계층): ADMIT → **출력을 매번 소비하는 메시지 재생 추론 70회, 실패 0**,
피크가 내내 **정확히 `per_call`**(9,382,092), `peak_within_admitted_budget: true`.
이것이 계획서 §3.3·§4.3이 물은 **배포 경로의 수명주기 답**이다 — 결과를 버리는 호출이 아니라 매번
읽어 소비하는 호출로 70회를 돌려도 계약이 가정한 값을 넘지 않는다.
(로그의 `EXIT=124`는 하네스의 `timeout -s INT` 종료이고, 앱 자신의 카운터가 70/70·실패 0을 기록한다.)

**cFS의 `B−1` 셀은 빌드가 불가능하다** — 그리고 그것은 실측된 사실이지 회피가 아니다. 앱의 예산은
컴파일 타임 매크로(`AI_LEARNER_BUDGET_BYTES`)이므로 `bounded > budget`이 정적으로 참이 되고, 컴파일러가
admission 이후 코드를 죽은 코드로 제거해 빌드 자신의 검증이 실패한다:

```
51_build_cfs_aarch64: ERROR: contract sha256 ecffe6e0... not found in ai_learner.so
```

CLAUDE.md의 환경 함정 표가 기록해 둔 그 조건이 그대로 재현됐다. **결과는 fail-open이 아니라 빌드
거부**다. 다만 이는 **계획서 §3.2가 "런타임 설정 예산으로 준다"고 적은 것이 실제로는 불가능**하다는
뜻이며, 계획의 오류로 기록한다(앱에 런타임 예산 손잡이가 없다). 따라서 cFS 층의 DENY 동작에 대해
이 실험이 말할 수 있는 것은 **"예산 미달은 배포 전 빌드에서 걸린다"**까지다.

## 4. D59 — 승인은 한 숫자로, 검증은 다른 숫자로 (계획서 Q3 미달)

계획서 §4.3-6은 **"피크가 승인 근거 예산을 넘지 않는다"**를 요구했다. 조건부 셀에서 넘었다.

```
admission : ADMIT_CONDITIONAL_MAP, budget_bytes = 9,382,092  (= per_call, map 분기 상한)
map_branch: module_ptr_mod64 = 0, hal_peak_after_append = 0, arm = "map"   ← E29b의 두 검증 다 통과
run       : hal_device_bytes_peak = 9,984,204   (승인 예산의 106.4%)
            peak_within_bounded = true          ← bounded(18,222,796)와 비교하기 때문
```

**초과분은 정확히 602,112 B = 입력 텐서 하나**(150,528 × 4)다. 원인은 논증이 아니라 산술로 확정된다:

```
per_call 9,382,092 = io 602,124 + transient 8,779,968
io       602,124   = 입력 602,112 + 출력 12
peak     9,984,204 = per_call + 602,112        (정확히 일치)
```

즉 **`per_call`의 io 항은 동시에 살아 있는 입력 텐서를 하나로 센다.** 초기화 때 만든 상주 입력 버퍼를
그대로 둔 채 샘플마다 입력 버퍼를 새로 할당하는 재생 패턴은 입력이 **둘** 살아 있으므로 그 전제를
어긴다. 계약이 틀린 것이 아니라 **배포가 계약의 전제를 어겼고, 아무도 그것을 탐지하지 않았다.**

**그리고 탐지하지 못한 이유가 결함이다(D59)**: `peak_within_bounded`는 *무조건 계약이 건전한가*를
답하지 *이 배포가 승인받은 예산 안에 있었는가*를 답하지 않는다. 두 값은 무조건 계층에서만 같다.
D53이 세운 규칙(*"어느 숫자로 승인했는지와 어느 숫자로 검증하는지가 같은지 확인하라"*)을 **추론 이후에
도는 검사에서 다시 어긴 것**이며, E29b는 그 규칙을 *분기 판정*에만 적용하고 이 사후 검사는 `bounded`와
비교하도록 남겨 두었다.

**E29·E29b가 볼 수 없었던 이유**: 그 실험들의 조건부 셀 모델은 입력이 수십 바이트라(mlp16k 36 B) 같은
구조적 초과가 수치로 드러나지 않았다. SmartCam의 입력은 602,112 B다.

**수정**: 두 C 경로가 승인 근거 예산을 스스로 유도해 `admitted_budget_bytes`·
`peak_within_admitted_budget`·`admission_mode`를 함께 보고하고, cFS 앱은 초과 시 EVS **ERROR** 이벤트를
올린다. `peak_within_bounded`는 **제거하지 않는다** — 계약 건전성과 배포 준수는 서로 다른 질문이고 둘 다
필요하다.

### 4.1 대조 — 초과분이 재생 패턴에서 온다는 것을 논증이 아니라 대조로 확정

**같은 예산·같은 조건부 승인에서 동치 재생만 끈** 셀을 돌렸다.

| 셀 | 조건부 승인 | 분기 | 동치 재생 | HAL 피크 | 승인 예산 대비 |
|---|---|---|---|---:|---:|
| A-cond (재생 있음) | ADMIT_CONDITIONAL_MAP | map | 5샘플 | **9,984,204** | **106.4%** |
| A-cond (재생 없음) | ADMIT_CONDITIONAL_MAP | map | 없음 | **9,382,092** | **100.0%** |

재생 없는 셀의 피크는 **`per_call`과 정확히 같다**. 두 셀의 차이는 재생 여부 하나뿐이므로 초과분
602,112 B는 전적으로 그 패턴의 두 번째 입력 버퍼다.

이 대조는 부수적으로 **E29의 이분성(map 분기 → 피크 = `per_call` 정확히)이 8.9 MB 실물 모델과
AArch64에서 그대로 재현**됨을 보인다. E29는 합성·소형 모델 7개에서 그 등식을 세웠다.

**cFS 앱의 두 모드도 상주 입력 버퍼를 재사용**하므로 같은 조건에서 피크가 `per_call`과 정확히
같았다(9,382,092). 즉 초과는 배포 어댑터의 성질이 아니라 **재생 하네스의 호출 패턴**의 성질이며,
그래서 이 발견은 "계약이 가정하는 호출 수명주기가 실제 경로에서 성립하는가"라는 검토서 §9.4의 질문에
대한 실측 답이다: **성립하려면 동시에 살아 있는 입력 버퍼가 하나여야 한다.**

## 5. 모드 분리 (계획서 §3.4)

앱이 남기는 레코드로 두 모드가 구분된다.

| 모드 | 입력 | 이 실험에서의 용도 |
|---|---|---|

샘플 순서를 파일에서 추측하지 않고 명시적으로 받아 fixture 매니페스트 해시와 대조한다(불일치는 거부).

## 7. 하지 않은 것 (범위)

- **정확도**: 라벨 정답률은 평가셋이 없어 다루지 않는다(E30·E31과 동일).
- **지연·처리량**: 게스트는 TCG 에뮬레이션이고 호스트는 `FUNCTIONAL_ONLY`다. **어떤 시간 수치도 성능
  근거로 인용하지 않는다.** 로그의 `*_us`는 실행 가능성 기록일 뿐이다.
- **공식 OnAIR 경로**(단계 3), **다른 모델**(단계 4), **공정한 기준선**(단계 5).
- **실물 보드**: QEMU 게스트다. RTEMS 실행이라고 부르지 않는다.
- **전체 RAM 수용성**: 계약은 IREE HAL 소유 할당의 부분 계약이다.
- **cFS 층의 런타임 DENY**: 앱 예산이 컴파일 타임 상수라 도달 불가(§3).
