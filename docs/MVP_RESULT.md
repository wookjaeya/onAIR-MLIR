# MVP go/no-go 결과 — CompiledLearner vs Python Learner in OnAIR

**TOPIC** / 연구노트 §29가 지정한 최초 go/no-go 실험(B0 vs B1)을 실제 OnAIR 플러그인 인터페이스 위에서 수행한 결과.
**Problem** / 컴파일된 Learner가 Python Learner보다 느렸고, 모델을 키워도 격차가 좁혀지지 않았다 — H1을 현재 형태로 유지할 수 없다.
**Solution** / 원인을 마샬링이 아니라 lowering 품질로 특정했고, 그 결과 연구의 무게중심을 "AOT가 빠르다"에서 "lowering 선택이 실행 특성을 지배한다"로 옮겨야 함을 보인다. H2는 오히려 강화된다.

> 주의: 실행 플랫폼의 timing_grade는 `FUNCTIONAL_ONLY`(1 vCPU, ratio_p99 1.67). 아래 절대 수치는 증거가 아니라 **방향성 관측**이며, 동일 호스트에서 연속 측정한 구현 간 비율만 논의한다.

## 1. 통합 결과 (성공)

- `CompiledLearner`와 `PythonLearner`를 OnAIR의 `AIPlugin`을 상속해 구현하고, OnAIR 자신의 로더(`onair.src.util.plugin_import.import_plugins`)로 적재해 CSV 텔레메트리 소스로 완주시켰다.
- 즉 연구노트 §6–7의 전제("OnAIR core를 바꾸지 않고 컴파일된 Learner를 삽입할 수 있다")는 **검증됨**.
- 함정: `AIPlugin.__init__`이 `ServiceManager()` 싱글턴을 만들며, 첫 인스턴스화 전에 `ServiceManager({})`로 초기화하지 않으면 `ValueError`로 실패한다.

## 2. 모델 크기 스윕 (L1 커널 경계, median)

| hidden | compiled (µs) | numpy/BLAS (µs) | compiled/numpy |
|---:|---:|---:|---:|
| 16 | 13.1 | 1.9 | 6.9× |
| 64 | 13.8 | 1.9 | 7.1× |
| 256 | 15.3 | 2.1 | 7.4× |
| 1024 | 22.0 | 3.1 | 7.0× |
| 4096 | 51.5 | 5.4 | 9.5× |
| 16384 | 152.5 | 17.9 | 8.5× |
| 65536 | 775.8 | 123.4 | 6.3× |

**교차점이 없다.** 모델을 4096배 키워도 컴파일된 쪽이 6–9배 느리다.

## 3. 원인 규명 — 마샬링이 아니다

항등 함수(`return %x`)만 담은 아티팩트의 IREE 호출 비용:

```
identity-call  median 4.70 us   p99 12.06 us
```

마샬링 고정비는 약 5 µs다. hidden=65536에서의 격차 652 µs를 설명하지 못한다. 따라서 원인은 **커널 코드 품질**이다. 베이스라인 NumPy는 최적화된 BLAS GEMV를 호출하는 반면, 손으로 쓴 `linalg.matmul`을 기본 플래그로 내린 커널은 그에 미치지 못한다.

## 4. 결정적 관측 — lowering 설정이 실행시간을 지배한다

hidden=16384, 동일 MLIR, 동일 런타임(local-sync), 플래그만 변경:

| lowering 설정 | median (µs) | p99 (µs) |
|---|---:|---:|
| default | 141.2 | 218.7 |
| `--iree-llvmcpu-target-cpu=host` | **82.3** | 135.2 |
| `+avx2,+fma` | 154.0 | 220.5 |
| `+avx512f,+avx512bw,+avx2,+fma` | 96.4 | 157.4 |
| (참고) numpy BLAS | 17.9 | 37.5 |

설정 간 편차 **1.87배**. 그리고 직관에 반해 `avx2` 명시가 default보다 느리다. 이것은 "성능 좋은 플래그를 고르면 된다"가 아니라, **어떤 설정이 데드라인을 만족하는지는 선험적으로 알 수 없고 측정·선택 절차가 필요하다**는 뜻이다.

## 5. 가설에 대한 판정

| 가설 | 판정 | 근거 |
|---|---|---|
| **H1** (AOT가 tail·jitter를 개선) | **현재 형태로는 기각 방향** | 모든 크기에서 컴파일 쪽이 6–9배 느림. 강한 베이스라인(BLAS)을 상대로는 "AOT = 빠름"이 성립하지 않음 |
| **H2** (계약 인지 lowering이 시스템 이득) | **강화됨** | 동일 모델에서 설정만으로 1.87배 편차, 순위가 직관과 불일치 → 선택 문제가 실재 |
| **H3** (사전 판정 가능성) | **미검증** | 실행시간 경계가 확정되지 않아 아직 평가 불가 |

## 6. 연구 방향 수정 (핵심)

1. **주장 축을 바꾼다.** "AOT가 더 빠르다"가 아니라 "**lowering 선택이 실행 특성을 지배하며, 그 선택을 미션 타이밍 제약으로부터 유도할 수 있다**"로. C3(contract-aware lowering/selection)이 유일한 살아남는 컴파일러 기여이며, 이번 결과가 그 필요성을 실증한다.
2. **베이스라인을 정직하게 유지한다.** B0는 BLAS를 쓰는 강한 베이스라인이다. 이를 약화시켜 승리를 만들면 안 된다. 대신 B0가 만족하지 못하는 축(메모리 상한, 정적 할당, 결정성, 비행 타깃 이식성)에서 비교해야 한다.
3. **비교 축을 지연에서 예측가능성·자원으로 옮긴다.** 이번 데이터에서도 default 대비 host_cpu는 median뿐 아니라 p99/median 비(1.55 → 1.64)가 달라진다 — 지연과 예측가능성이 함께 움직이지 않는다는 신호.
4. **A-native 변형이 필수다.** Python 래퍼를 유지하는 한 5 µs 마샬링이 항상 붙는다. cFS C 앱으로 승격한 변형에서만 계약이 의미를 갖는다.

## 7. 다음 실험 (우선순위)

1. lowering 후보 집합을 넓혀(타일 크기, 벡터화, `link-embedded`, 스레드 수) **설정→(median, p99, peak memory)** 매핑을 만든다. 이것이 §10의 `L_m`이다.
2. 동일 매핑을 ARM64 실기(격리 코어, `platform_check` PASS)에서 재측정한다.
3. B2(TFLite Micro)를 추가해 "MLIR이어야 하는가"에 답한다.
4. A-native 변형(cFS C 앱 내 정적 링크)에서 마샬링 제거 효과를 분리 측정한다.
